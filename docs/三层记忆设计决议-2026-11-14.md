## 背景

当前 `logs` 表只有 `text`（完整正文），检索时返回全文，实测：
- `/search?limit=3` 返回 **5019 字节**，而模型只为判断"哪条相关"就要读 5KB
- 加 `?summary=1` 后降到 **973 字节**（省 81%），但摘要只是**截断正文前 80 字**，
  经常截在句子中间，且**丢失技术名词**（实测 `rebindDbStore` / `VACUUM INTO` /
  `busy_timeout` / `conversation.view` / `replaceRisk` 五个词全部不在正文前 40 字，
  若摘要只写"完成了什么"，这些词将永久搜不到）

## 结论：三层（渐进式披露 / Progressive Disclosure）

学术与工程界的通用名称是 **渐进式披露（Progressive Disclosure）**，
在记忆系统语境下常称 **渐进式记忆展开（Progressive Memory Disclosure）**
或 **摘要优先的分层记忆（Summaries-first Hierarchical Memory）**。

| 层 | 内容 | 存储 | 用途 |
|---|---|---|---|
| **L0** | `topic`（现有 13 类） | 已有 | 分类筛选 |
| **L1** | `summary`（≤35 字）+ `keywords` | **待新增** | 一眼判断 + 关键词命中 |
| **L2** | ~~详细摘要~~ | **不做**（用户决定：我们每次存的内容并不多，中间层是冗余） | — |
| **L3** | `text`（现有） | 已有 | 精确回溯 |

### 参考系统（已联网查证，全部真实存在）

- **TierMem**（[arXiv 2602.17913](https://huggingface.co/papers/2602.17913)）——
  两层：summary tier + **不可变原始日志**。核心论点「write-before-query barrier」：
  写时压缩发生在知道未来查询之前，摘要会产生**不可验证的遗漏**（unverifiable omissions）。
  **对我们的启示**：`text` 必须保持不可变、可追溯，摘要永远不能替代它。
- **APDMem**（[ACL EMNLP 2026 industry](https://aclanthology.org/2026.emnlp-industry.81/)）——
  四层：thematic summaries / personalized key facts / turn-level evidence notes / raw messages。
- **RAPTOR** —— 递归摘要树，面向长文档（不适用我们）。
- **concinno-skills-memory**（[PyPI](https://pypi.org/project/concinno-skills-memory/0.1.0/)）——
  三层 index(≤100字)/summary(≤500字)/archive，与我们的设计最接近。

## 已确认的 6 条决策

| # | 问题 | 决定 |
|---|---|---|
| 1 | 强制关键词遇无名词怎么办 | **允许写「无」**，不硬凑（技术讨论类本来就抽象，实测 #480/#476/#470 关键词全为空） |
| 2 | keywords 分隔符 | **不用逗号**（逗号是中文常用标点，会与正文混淆）→ 用中文不常用的符号，具体待定（候选：`｜` 全角竖线 / `·` 间隔号 / `;` 分号） |
| 3 | 老数据摘要怎么办 | **迁移时批量写入 text 前 40 字作兜底**（一次性 UPDATE，不让检索时实时截断） |
| 4 | 清空时机 | **先验证再清理**（450 条真实数据是唯一能验证「老数据兜底路径」的依据，清空后无回滚） |
| 5 | `seg` 列的 bm25 权重 | **先给 0 测试**（`seg` 只用于中文逐字分词检索，不该影响排序） |
| 6 | bm25 排序方向 | **由模型决定**（已查证：bm25 返回负分，越负越相关 → 必须 `ORDER BY score ASC`，现有代码需核对） |

## 实施时的 7 个坑（已确认）

1. **FTS5 不能加列**。官方明确「加列是 relying on undocumented behavior」
   （[SQLite 论坛](https://sqlite.org/forum/forumpost/3a8e4f4a9d128fa5?raw)）。
   必须 `DROP TABLE logs_fts` → `CREATE` 新结构 → **450 条全部重新 INSERT**。
   漏这步 = 检索在新表里查旧索引 = 什么都搜不到。

2. **bm25 权重个数必须等于 FTS 表列数**（**含 UNINDEXED 列**），且按声明顺序。
   权重写少了会直接报错或错位加权。

3. **标记正则从 3 组变 5 组**：`[1]=kind [2]=topic [3]=summary [4]=keywords [5]=正文`。
   **2026-11-14 已经因为捕获组错位丢过全部流水**（正则只剩 2 组，处理代码按 3 组取值
   → topicRaw 拿到正文、body 恒空 → 所有带标记回复静默丢弃）。
   改完必须立刻跑 `_dbpreview/test-marker-forms.mjs`（它现在断言组数和 body 非空）。

4. **模型可能不写 summary**。写入时若 summary 为空，记一条 `[summary-missing]` 诊断日志。
   跑一段时间查比例，>20% 说明约束不够强。

5. **「技术讨论强制列关键词」会冲突**。技术讨论类最抽不出名词（实测三例全空）。
   允许写「无」，不要硬凑（硬凑会污染检索）。

6. **GUI 要跟着改**。六个页签里「记忆流水」页现在显示 `text`，
   加 summary 后列表应显示 summary（短，一屏能看更多），点开才显示全文。
   `client.js` 是浏览器模块，改完**必须完整重启客户端**（插件重载不刷新浏览器代码）。

7. **schema 版本路径**。改 `MIGRATIONS` + 升 `SCHEMA_VERSION` 到 3。
   必须**同时测两条路径**：①现有库迁移（450 条老数据）②空库全量建（清空后重建）。

## 实施记录（2026-11-14，与决议不同的地方）

| 决议原文 | 实际实现 | 为什么 |
|---|---|---|
| keywords 分隔符「待定」（候选 `｜` / `·` / `;`） | **全角竖线 `｜`** | 用户选定；中文正文几乎不出现，不与逗号混淆 |
| 决议 #5：`seg` 列 bm25 权重**先给 0** | **给 1**，并按 keywords 3 / summary 2 / text 1 / topic 1 加权 | 中文查询是**逐字命中 `seg`** 的（text 列对中文整段成词）。seg 权重给 0 会让所有中文命中同分、排序退化成入库顺序 —— 实测核对后改为 1 |
| summary / keywords 作为独立「层」 | 写在**标记行里**（与 topic 同一行，顺序固定） | 与 topic 同样的解析路径，不新增通道；顺序写反会被前一个参数吞掉，`sanitizeKeywords` 有截断兜底 + `[summary-missing]` 诊断 |
| 决议说 80 字截断兜底 | 真摘要 ≤35 字；老数据迁移时写入 `substr(text,1,40)`；检索时无 summary 才回退正文 80 字 | 35 字是注入预算内的可读长度；40 字是迁移兜底（一次性写库，不是查询时截断） |
| 「不要选 SUM」 | `seg` 的内容 = `summary + keywords + text` 的中文逐字切分 | 摘要/关键词里也有中文（如「行号重算」），不并进 seg 就永远搜不到 |
