## 1. 项目定位

**「大肥鱼的梦」** —— DeepSeek Harness 的长期记忆插件，面向**个人开发者 / 小型项目**。

一句话：**零工具**。模型不调用任何 `memory_*` 工具，记忆的读写靠注入 + 回复正文里的标记。

存在的理由：工具 schema 会进入每次请求的 `tools` 数组，通道校验严格时
**一个工具写坏 = 整个请求被拒 = 该 profile 下所有会话无法发消息**。
为此实际中断过两次，每次都要手动卸载插件才能恢复。

**为什么用 SQLite 而不是 Markdown**：驱动它的不是容量（实测 5 万条才 17.8MB），
而是**查询形态** —— 用 `.md` 按主题检索只能靠 grep 做子串匹配，换个说法就搜不到；
而 SQLite 的 FTS5 能分词、`GROUP BY` 能自动生成索引、`UPDATE` 能改错。

### 3.4 注入层（核心）

`ctx.systemPrompt.context({ name: 'plugin:dsh-fatfishdream-memory', order: 300 })`，入口 **L2123**。

**分流逻辑**：

```
if (getDbStore()) renderFromDb(...)        // 主路径（也是唯一路径）
                ↓
          finishInjection(parts, config)   // 统一收尾：加使用说明 + 标题
```

| 函数 | 位置 | 职责 |
|---|---|---|
| `renderFromDb` | L2181 | 全局结论 + 全局规则 + 项目段 + **记忆索引（路由表）** |
| ~~`renderFromFiles`~~ | — | 已于 2026-11-13 删除（`.md` 回退路径不再存在） |
| `finishInjection` | L2253 | 拼「记忆使用说明」+ 标题 |
| `usageLines` | L2268 | **说明正文**，`dbMode` 与非 dbMode 两套；改这段等于改模型行为 |

**`renderFromDb` 输出的四段**：

1. `## 全局结论` —— `profile` 全部 active + `rules` 里 `scope='__global__' AND kind='pref'`
2. `## 全局规则` —— 仍读 `policy.md`（行为规则要求每轮必达，与偏好分账）
3. `## 项目结论（<项目名>）` —— `rules` 里 `scope=<项目名>` 的 active（redline 优先排序）
4. `## 记忆索引` —— **路由表**，`GROUP BY topic` 现算，告诉模型「记忆里有什么、去查什么」

> **路由表为什么不存储**：存下来会过期，而聚合永远准确。
> 它解决的是「模型不知道要查什么，就不可能去查」这个根本问题。

### 3.5.1 原文归档通道（v4，2026-11-14）

```
assistant/message → handledMessageIds 去重(turn:step) → appendArchive(role='assistant') → 再解析 mem-log
user/message      → appendArchive(role='user')        → 再过情绪形态闸门 → analyzeEmotion
```

**三条不能改的边界**（改错会静默丢原文或污染结论层）：

1. **归档在一切判断之前**。user 侧必须排在 `emotion-skip` 闸门之前 ——
   被闸门拦下的「提示词形态」消息也要留档；assistant 侧必须在 `hasMarker` 判断之前，
   没有 `mem-log` 的回复同样要存。
2. **归档失败只记诊断，不抛**。`diag('archive-write-failed', {role})`，
   绝不能因为归档出错而中断标记写入或情绪录入。
3. **archive 不进注入、不进默认 `/search`**。`db-store.search` 只查那四张表；
   原文层只能走 `listArchive`（HTTP `/archive`）。

### 3.6.1 解析层记账（2026-11-14）

写入本身几乎不失败：实测一天 **108 次 `mem-写流水` / 0 次 `mem-写入失败`**，
但同期有 **5 轮（4.6%）「正文里有标记、一条都没落库」**，其中两轮**一行日志都没有**。
丢的不是写入，是解析：

| 形态 | 现象 | 现在记什么 |
|---|---|---|
| topic 与正文同行（`test-marker-forms` 的 form F） | 正文被 `[^\n]*?` 吃进 topic → `body === ''` | `marker-dropped` + `reason:'empty-body'` + `topicRaw` |
| 整条压成一行 / 没写收尾符（form E） | 正则零匹配，连 `continue` 都不进 | `marker-unmatched` + 正文头 80 字 |
| 库不可用 / 清洗后为空 / 写异常 | 各自 `continue` | `marker-dropped` + 对应 `reason` |

判据（`_dbpreview/selfcheck-marker-hardened.mjs` D 段守着）：

- `hasMarker && markerMatched === 0` → `[marker-unmatched]`
- `hasMarker && markerWritten === 0` → `[marker-dropped]`

⚠️ 两条只在**失败**时出现，正常写入仍只有 `[mem-写流水]`。
排查「模型说写了、库里没有」先看这两条 —— 以前它在日志里和
「这轮本来就没写」长得一模一样。

**为什么改而非删**：数据实测 239 条流水里 **19.2%** 是「只有错误/技巧、没有写操作」
的认知性事件 —— 光靠「有写操作」判断会全漏。根本问题是判断依据错了：
模型发现自己犯错、发现更快的做法，往往不碰文件。

## 4. `db-schema.mjs` 结构

### 4.1 四张业务表 + 一张原文层

**不是单表**。v2 起按「生命周期与访问方式」拆成四张业务表，v4 又加了第五张 `archive`，
`SCHEMA_VERSION = 4`（L32）。

| 表 | 量级 | 谁写 | 是否注入 | 关键列 |
|---|---|---|---|---|
| `profile` | 极小 | 人工（GUI） | ✅ 每轮 | `id ts topic text status writer review review_note updated` |
| `rules` | 小 | 人工（GUI） | ✅ 按项目 | 上面全有 + **`scope`** + **`kind`**（redline/pref/state） |
| `emotion` | 中 | **插件自动** | ❌ | `id ts cls quote evidence confidence score text status review review_note writer` |
| `logs` | 大 | 人工（mem-log） | ❌ | `id scope ts topic summary keywords text status writer`（v3 加了两层） |
| **`archive`** | **大（最大）** | **插件自动（v4）** | ❌ | `id ts scope role text session_id turn step` —— **原文层**，一条不落 |

- `profile` 无 `scope`（画像是跨项目的）；`logs` 现在 9 列（v3 加了 `summary` / `keywords`），没有 `review` / `review_note` / `updated`。
- **历史迁移行的 `ts` 可能为 NULL**（2026-11-14 实测：`profile` 11 条里 9 条、`rules` 136 条里 109 条）。
  这是早年写入路径没有时间戳留下的，**不是 bug，也不要用今天的日期回填** ——
  那是编造时间。代码不依赖 `ts` 排序（`TS_ORDER` 用 id），注入也不受影响；
  只有「按时间筛选」时这些行会缺席，接受即可。新写入一定带 `ts`（`insertInto` 统一生成）。
- **`topic` 是可选列**：为空的行不进「记忆索引」（`routeTable` 过滤 `topic IS NOT NULL`），
  但照常注入。用户手工维护时忘了填 topic 属于正常情况，不报错。
- `rules.scope` 默认 `'__global__'`；其余为项目名。
- **v1 的 `entries` 表仍在库里**（拆表时保留作可回退的历史），代码不再读写它。

**索引**（8 条属于四张业务表 + 3 条属于 `archive`，另有 `idx_kind_status` / `idx_scope_kind` / `idx_ts` / `idx_topic`
四条是 v1 `entries` 表留下的，**已无作用，不要删也不要照抄**）：
`idx_profile_status`、`idx_rules_scope`、`idx_rules_topic`、`idx_emotion_ts`、
`idx_emotion_status`、`idx_logs_ts`、`idx_logs_scope`、`idx_logs_topic`；
`archive` 三条：`idx_archive_ts`、`idx_archive_scope`、`idx_archive_role`（都带 ts，回溯按时间倒序）。

### 4.2 FTS5 与中文检索（最容易踩的坑）

**五张**表各有一个 contentless FTS 表：`profile_fts` / `rules_fts` / `emotion_fts` / `logs_fts` / `archive_fts`
（前四个在 `CREATE_FTS` L175–180，`content=''`, `tokenize='unicode61'`；`archive_fts` 在 `MIGRATIONS` v4 里建）。

**v3 起 `logs_fts` 是 5 列**：`summary, keywords, text, topic, seg`（建表语句 L188 的
`LOGS_FTS_V3`，由 `MIGRATIONS` v3 重建）。列顺序就是 bm25 权重的顺序，二者必须同时改。
另外三张业务表仍是 3 列（`text, topic, seg`），**v4 的 `archive_fts` 只有 2 列**（`text, seg`，原文层不需要摘要），
全部用 `FTS_COLUMNS`（L310）区分。

**实测结论**：

| tokenizer | 中文表现 |
|---|---|
| `unicode61` 裸用 | 整段中文成一个 token → 搜「沙箱」永远 0 条 |
| `trigram` | 要求查询词 ≥3 字符 → 「沙箱」「像素」等 2 字词全 0 条 |
| **逐字分词 + unicode61** | ✅ 全部命中，英文标识符也正常 |

**做法**：写入时把中文逐字空格隔开存进 `seg` 列，检索时同样拆分用 AND 连接。

```js
segmentCjk('沙箱拒绝 write')  // → "沙 箱 拒 绝 write"
buildMatchQuery('沙箱')       // → "\"沙\" AND \"箱\""
```

### 4.3 contentless 表的限制

五个 `*_fts` 都是 `content=''`。**不能直接 `DELETE`**，
会报 `cannot DELETE from contentless fts5 table`。必须用 `'delete'` 命令并提供原值：

```js
// 更新时必须先按旧值 delete，再插新值
INSERT INTO ${fts}(${fts}, rowid, summary, keywords, text, topic, seg)
VALUES('delete', <id>, <oldSummary>, <oldKeywords>, <oldText>, <oldTopic>, <oldSeg>)
```

**这是 `db-store.mjs` 的 `updateText` 必须先 `SELECT` 旧值的原因**（`db-store.mjs` 的 `updateText`）。
`syncFts(db, table, id, row, oldRow)` 用**对象**传值（不是位置参数）—— logs 5 列、archive 2 列、其余 3 列，
位置参数很容易把 summary 传成 topic 而无人察觉。

### 4.4 schema 版本管理

```js
PRAGMA user_version   // 当前版本号，应为 4
```

启动时检查（`openMemoryDb` L382）：版本比代码新 → 抛错要求升级插件；比代码旧 → 逐级跑 `MIGRATIONS`（L205）。
**改 schema 必须同时加一条 `MIGRATIONS` 条目并升 `SCHEMA_VERSION`**，否则老库升不上来。

**v4 迁移只建表、不动数据**：`MIGRATIONS[3]`（version 4）执行 `CREATE_ARCHIVE`（L158，幂等）
+ 建 `archive_fts`。历史对话**不回填** —— 归档从改版那一刻开始积累，
因为「当时到底说了什么」已经不是可靠信息了，回填等于编造。

**v5 迁移（2026-11-14）三件事**：`confidence` 归一化（`高置信→high` / `NULL→legacy`）、
删 v1 的 `entries` 冷存档、以及**迁移后 VACUUM**（`MIGRATIONS` 条目带 `drops: true` 时才跑）。
> ⚠️ 删 FTS 虚拟表时**只能先 DROP 本体**（`entries_fts`），
> 直接删 `entries_fts_data` / `_idx` / `_config` 会抛
> `table xxx may not be dropped` —— 影子表由 SQLite 连带清理。
> 不 VACUUM 的话体积一分不省：实测 1312 KB → 1348 KB（反而涨），VACUUM 后回落到 392 KB。

### 6.2 检索的项目隔离（2026-11-13）

**变更**：`search()` 从「可选过滤」改为**硬隔离**。此前 `projectName` 虽在签名里，
但两个调用方（`/memory search` 与 HTTP `/search`）都没传 —— 等于全库检索。

**为什么必须隔离**：用户原话「其他项目的记忆看多了会出现 AI 幻觉」。
别的项目的经验是**看起来能用、实际不适用**（如 ForzaOverlay 的 HUD 坐标套进 FatFishDream），
比「没搜到」更糟 —— 模型会自信地用错且无从察觉。

| 表 | 隔离规则 |
|---|---|
| `rules` | `scope=<本项目>` **或** `scope='__global__'`（全局规则本就跨项目） |
| `logs` | 只 `scope=<本项目>` |
| `profile` | **不隔离** —— 画像是「用户这个人」，天然跨项目 |
| `emotion` | **不在检索池**（v5）—— 情绪是「个人兴趣记录」，只给用户在 GUI 看。它的 `text` 是模板句（分类名+证据+置信度全进 FTS），会挤占结论层结果位 |

**用法**：

```
/memory search <词>      只搜本项目（+ 全局规则、画像、情绪）
/memory search! <词>     显式跨全部项目
GET /search?q=..&project=X   隔离到 X
GET /search?q=..&all=1       跨项目
```

**实现要点**：`search(query, { projectName, crossProject })`。
`isolate = !crossProject && projectName != null`。
不传 `projectName` 时仍全库（保留给测试与旧调用）。

> **为什么没拆成每项目一个库**：过滤能力本来就有，只是没人传参 —— 改 2 处调用即可；
> 拆库要改 db-store、全部路由、迁移、GUI 项目切换（数百行），且**破坏跨项目查看**
> （用户偶尔要看别的项目）、增加备份漏项风险、5 份 WAL。收益为负。

下面是分页部分的说明。

**为什么分页**：流水只增不减，界面若一次拉全量，每切一次页签就重查一遍大结果集；
而人几乎不会往下翻。现在固定 **每页 30 条**，且可翻范围只到**最近 100 条**（约 4 页）。
更早的内容仍在库里，靠 `/memory search` 检索，不占界面资源。

| 环节 | 实现 |
|---|---|
| 前端常量 | `client.js` 的 `PAGE_SIZE = 30` / `MAX_VIEWABLE = 100`（L633 / L634） |
| 请求参数 | 流水页传 `limit=PAGE_SIZE&offset=page*PAGE_SIZE&cap=MAX_VIEWABLE`（L666–668） |
| 后端 cap | `db-store.mjs` 的 `listEntries({cap})`：取「第 cap 新的那条」的 `(ts,id)` 作下界过滤 |
| 返回值 | `listEntries` 现在返回 **`{ rows, total }`**（不再是裸数组），`total` 已按 cap 封顶 |
| 页码归零 | `useEffect` 监听筛选条件，一变就 `setPage(0)`（否则会停在越界 offset，显示「没有条目」） |

**cap 的关键实现细节**：不能用 `LIMIT cap` 了事 —— 那样翻页时算不出正确总数。
正确做法是先查第 cap 新的那条的 `(ts, id)` 作为边界，再在主查询上加
`AND (ts IS NULL OR ts > ? OR (ts = ? AND id >= ?))`，用**复合条件**避免同 ts 多条时漏行。
自检见 `_dbpreview/selfcheck-cap.mjs`（12 项，含「被排除的全早于保留边界」的断言）。

> ⚠️ **判断新旧不能用 `id`**：迁移进来的历史数据 id 不按时间顺序分配。
> 排序真实依据是 `ORDER BY ts IS NULL, ts DESC, id DESC`。
> 2026-11-13 自检时用 id 判断，误报了一次「cap 边界错误」。

**组件**：`EntryRow`（L294，单条记忆；流水有 `summary` 时先显示摘要，点「展开全文」看正文）· `AddRuleForm`（L461）· `PersonaNormCard`（L556）·
`MemoryPanel`（L609）· `SidebarIcon`（L1288）。

**标记擦除器**（2026-11-13 新增）：`MEM_STRIP_RE`（L1339）/ `MEM_PARTIAL_RE`（L1353）/
`stripMemMarkers`（L1361）/ `ensureBlankStyle`（L1430）/ `installMarkerScrubber`（L1467），
挂载在 `ctx.effect`（L1594）。

> ⚠️ **擦除器不许删 DOM 节点**（2026-11-14 闪烁事故）：旧实现在擦完变空的元素上
> 调 `el.remove()`，那是在 React 管理的 DOM 上删节点 —— React reconciliation
> 发现节点没了会重新插入，擦除器下一帧再删，表现为「每轮回复结尾一直闪烁才停」。
> `lastSelfWriteAt` 的 100ms 窗口挡不住（React 重渲染可能更晚）。
> 现在只改文本 + 打 `data-dsh-mem-blank` + CSS 隐藏，不改 DOM 结构。

**单条操作的按钮**：修改 / 停用 / 删除 / 升级为全局（`canUpgrade` 仅对 `rules` 且非全局）。

> **「停用」存在的理由**：升级为全局是单向的（防一键误导所有项目），
> 但人会点错。停用让条目不再注入、保留可恢复，比删除少一分心理负担。

**API 常量在文件头**（L7–15、L42–43）——加路由时要同步加常量，否则面板取不到数据。

**主题 token 只用确定存在的那些**，猜错会静默失效（踩过，见 AGENTS.md 硬约束 8）。

## 8. 数据流

### 读（每轮自动）

```
systemPrompt.context (L2123)
  → getDbStore() ?
      ├─ 是：renderFromDb (L2181)
      │    ├─ profile 全部 active + rules 全局 pref        ← 全局结论
      │    ├─ policy.md 的「给模型的规则」小节             ← 全局规则
      │    ├─ rules WHERE scope=<项目> AND status='active' ← 项目结论
      │    └─ GROUP BY topic（rules ∪ logs）              ← 记忆索引
      └─ 否：提示「记忆库不可用」（.md 回退路径已移除）
  → finishInjection (L2253)（加使用说明）
  → 返回文本
```

### 写（模型侧，不经过沙箱）

```
模型在回复正文写 <!--mem-log topic=.. summary=.. keywords=..-->
  → session/event 收到 assistant/message           （L2522）
  → 取 event.data.message.content   ← ⚠️ 比 user/message 多一层
  → 【v4】先 appendArchive(原文)     ← 不论有没有标记，都先归档
  → MEM_MARKER_RE 匹配
  → dbStore.appendLog(project, body, {topic, summary, keywords})
  → INSERT + syncFts
  → reportBudget + diag 记录
```

### 写（插件侧，不经过模型）

```
用户消息 → session/event（L2821）
  → 【v4】appendArchive(role='user')  ← 在形态闸门之前，被拦下的也留档
  → stripPolicyPhrases → 形态闸门（prompt-like / >1000 字 / >20 行 → emotion-skip）
  → analyzeEmotion
  → 每一条 hit 都 dbStore.recordEmotion → emotion 表（writer='plugin'），
    confidence 按 score 标 high / low，**不再按阈值丢弃**
  → 无 hit 的弱线索不入 emotion（没有类别可归），原文已在 archive 里
```

> **v4 的核心取舍**：以前靠阈值和模型裁决「这条算不算情绪」，判断本身就会丢信息；
> 现在**原文层全存**（archive），结论层（emotion/logs）只负责「挑出来给人看」。
> 判错了还能回原文追溯，这是「记忆就是完整的，而不是取舍」的落地方式。

## 9. 改动影响面（危险区）

| 改这里 | 会影响 | 要注意 |
|---|---|---|
| `db-schema.mjs` 的 `CREATE_*` / `MIGRATIONS` | **已有数据库** | 必须同时加 `MIGRATIONS` 条目并升 `SCHEMA_VERSION`，再写数据迁移脚本 |
| `segmentCjk` / `buildMatchQuery` | **所有中文检索** | 改错则检索静默失效（永远 0 条），不报错 |
| `syncFts` / `removeFts` 的调用时机 | FTS 索引一致性 | contentless 表必须按旧值 delete 再插入 |
| `renderFromDb` 的段落 | 每轮注入 | 段落顺序影响 prefix cache |
| **改 `mem-log` 参数（topic/summary/keywords）** | **模型每轮的写入行为 + 检索质量** | 正则必须**恰好 5 个捕获组**、顺序固定；改完立刻跑 `_dbpreview/test-marker-forms.mjs` |
| **`usageLines`（L2268）** | **模型每轮的写入行为** | 这是模型唯一会读到的使用说明；文档写错了没人看，这里写错了每轮都错 |
| `routeTable` | 模型能否找到历史 | 返回空 = 模型不知道记忆里有什么 |
| 注入预算 | 注入量 | **判据是注入字节，不是文件字节** |
| `joinWithBudget` 的截断方向 | **丢哪一批** | 从头截会丢最新的（已改为头 40% + 尾 60%） |
| `rules.scope` 的默认值 | **全局污染** | 默认必须是项目级；误判成全局会在错误项目里造成实际损害 |
| `findTableById`（L2677） | 所有只传 id 的接口 | id 在各表里**各自独立编号**，必须遍历；GUI 应优先显式传 `table` |
| **`appendArchive` 的调用位置** | **原文能不能追回来** | user 侧必须早于情绪闸门、assistant 侧必须早于 `hasMarker` 判断；挪到后面 = 静默丢原文 |

### ⚠️ 三个静默失效陷阱

**① FTS 分词改了 → 检索不报错，但永远 0 条**

`trigram` 要求 ≥3 字符，`unicode61` 对中文整段成词。
只有「逐字分词 + unicode61」两种语言都正常。改这里必须实测中文 2 字词。

**② contentless FTS 表不能 DELETE**

`DELETE FROM xxx_fts WHERE rowid=?` 会抛 `cannot DELETE from contentless fts5 table`。
必须用 `'delete'` 命令带原值。

**③ 健康自检写死数量 → 每次加功能都假报警**

`routes` 曾写死 `=== 3`，加到 14 条后一直 FAIL。现在改 `>= 3`，并在数据库模式下增加 `db:readable` 检查。

### ⚠️ 各表列不同：写 SQL 前先确认列存在

**2026-11-13 踩过**：`updateText` 对所有表无条件执行
`SET text=?, review='edited', updated=?`，但 **`logs` 表 9 列，仍没有 `review` / `updated`**
（见 §4.1）→ 抛 `no such column: review`，表现为「改流水正文失败」，
GUI 只报一个笼统错误，看不出是列不存在。

同理 `setTopic` 只能用于有 `topic` 列的 `logs` / `rules`，`profile` / `emotion` 没有。

**规矩**：写通用 SQL 前用 `PRAGMA table_info(<表>)` 取实际列，按存在的列拼语句。
新加表时尤其要注意。

### ⚠️ 不要在记忆正文里写完整标记示例

**2026-11-13 事故**：在一条记忆的正文里写了一个完整的标记示例
（含尖括号开头与 `-->` 结尾），`MEM_MARKER_RE` 把它当成**真标记**匹配了 ——
后面的说明文字顶替了正文，`topic` 被截成 75 字符的残句，两条脏数据进了索引。

**已加固**：正则加 `^` + `m` 标志，要求标记**必须在行首**。
这挡住了实际发生的这一种，但不是万全之策（行首写示例仍会中招）。

**写法规矩**：举例时把标记拆开 ——
写 `` `<!--mem-log` 做了什么 `-->` ``（前段和后段各用反引号包住、中间隔中文），
不要写成一整块连续的。注入里的 `usageLines` 一直是这么写的，是安全的。

### ⚠️ 加代码会让后面的行号成片失效

地图里的行号是**绝对位置**。在 `apply` 中间插入 50 行，它后面所有行号全部漂 ——
2026-11-12 实测三次：3 处 → 20 处 → 27 处全失效；
2026-11-13 拆表后又漂了一次，最大偏 **124 行**（`runHealthCheck` 3514 → 3639）。
2026-11-13 深夜再漂一次：迁移三 bug 修完后 `createStore` 1095 → 1156、
`usageLines` 2430 → 2592、`runHealthCheck` 3810 → 4138，**当时 89 处引用里有 40 处对不上**（修完并补了引用后共 109 处），
而 `verify-map.mjs` 只判「该行非空」，全绿通过 —— 假绿。见 §13 的 `chk-map-lines.mjs`。

**极小改动也会漂**：2026-11-13 修 `byKind`→`byTable` 时**只加了一行注释**（当时在第 3290 行），
该行之后的 21 处引用全部 +1（路由表 11 处、`runHealthCheck`、`webServer.register`、
健康自检调度…）。所以判据不是「改了多少行」，而是「改动行之后还有多少引用」。

**所以改完代码不能只改自己碰过的那几行，要全表重新核对。**

```js

  .filter(n => n <= idx.length).sort((a,b) => a-b)
for (const n of refs) console.log(String(n).padStart(5), (idx[n-1]||'').trim().slice(0,66))
```

输出来后逐行看：**该行内容是不是地图上说的那个函数/那一节**。对不上的就是漂了的。

**行号会漂移，结构不会。** 查代码时优先按「函数名」找，行号只当提示。

> ### ⚠️ `/entries` 不是模型入口，且 `table` 必须显式传
>
> **2026-11-13 修过一个静默失效**：该路由原来写 `q.get('table') || 'rules'`，
> 缺省时默默去查 `rules` 表。外部调用方传 `?kind=logs` 时就会落到这里 ——
> 以为在查流水，实际查了 `rules` 并附加 `kind='logs'` 过滤，返回 **0 条 + `ok:true`**。
> 现在 `table` 缺省会返回 400。
>
> **为什么只修这一个参数**：`kind` / `status` / `scope` 传错的语义是
> 「没有匹配项」，与真正的空结果无法区分，那属于调用方自己该保证的；
> 而 `table` 缺省是**静默换了一个查询对象**，会返回真实数据让人看不出错。
>
> **模型查记忆的正确入口是 `/search`**，不是 `/entries`：
> search 有 bm25 排序、跨四表 UNION；entries 是给 GUI 按表翻页用的。
> 注入里刻意不提 entries，就是为了不让模型走错门。

### 单独的一份说明：文档 ≠ 记忆

- **文档**（`docs/`、`README`、`AGENTS.md`）→ 仓库资产，给开发者看，进 git
- **记忆库**（`memory.db`）→ 运行时数据，模型每轮读，在记忆根目录

**文档永远不进数据库。** 这两者的读者、生命周期、分发方式都不同。
