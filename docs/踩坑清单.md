## ★ 2026-11-20 补记链排查出的六条（同一天第二批，同样「不报错」）

> 背景：补记（漏记自动补写）修好「拿不到根地址」之后，用户说
> 「不能完全排除，这个功能里还有隐性未发现的 bug」—— 于是逐条排查，
> 挖出这六条。**它们的共同点是「整块代码零回归覆盖」**：
> `_dbpreview/` 里 `backfill` 的命中是 **0 处**，
> 且那套代码**全是箭头函数**，连 `verify-functions` 的死代码检测都躲过了
> （它的覆盖边界明写着「只检查 `function` 声明」）。
>
> ⚠️ **2026-11-26 补注**：上面这句「命中 0 处」是**当时的现场**。
> 这六条修完之后已补三个脚本，现在 `grep backfill _dbpreview/` 是 **124 处**。
> 保留原文是为了记住「零覆盖时什么样」，**不要拿它当现状**。

- **事件顺序：在 serial 先跑的事件里清状态，会让后跑的事件恒读到空**（杀伤力最高）：
  `turn/end` 的漏记判据读 `logRouteHits.get(sid)`，而清理写在 **`turn-stopping`** 里。
  `turn-stopping` 是 serial、**先于** `turn/end` 执行 —— 于是那个量**恒为 0**。
  实测证据：全部日志 17 次 `backfill-check`，`routeHits` 分布是 `0 → 17 次`，
  **一次非 0 都没有**；17 组同轮对照，`streak` 全部早于 `backfill`。
  **后果不是「少一道保险」**：判据退化成只靠 `wroteCount`，
  而 `turnLogWrites` 也会被 `turn-stopping` 重置 → 「调过 `/log` 但没被认账」的轮次
  被判成「没写」→ **重复补一条已经写过的**。
  **修法是「搬位置」不是「删逻辑」**：清理移到 `turn/end`、读之后、**所有 return 之前**。
  直接删会让 Map 无限增长，且下一轮读到上一轮计数。
  **判据**：改任何一个「在 A 里写、在 B 里读」的状态之前，先确认 A 和 B 的**执行顺序**。

- **无超时的 I/O 会锁死一个 `busy` 标志，而表现是完全静默**：
  `runBackfillTask` 里 `fetch(...)` **没传 `signal`**，而 `pumpBackfill` 的
  `finally { backfillBusy = false }` 要等 `await` 返回才执行。
  `BACKFILL_TIMEOUT_MS` 只包住了模型调用，**没包住 POST**。
  实测复现（永不 resolve 的 fetch）：`3 秒后：backfillBusy = true, queue = 24`，
  再调 pump 仍是 `true` —— **永久死锁**。
  **表现**：后续每轮只有 `backfill-enqueued`，既无 `backfill-done` 也无 `backfill-failed`。
  **修法**：`AbortSignal.timeout(...)`（Node 18+ 内置，零依赖）。
  **判据**：凡是 `await` 一个外部 I/O 之后才放开的状态标志，**那段 I/O 必须有超时**。

- **写死了值、却没人读的字段 = 恒假分支**（AGENTS.md 已有规矩的又一个实例）：
  `runBackfillTask` 五个返回分支全写 `retryable: false`，而**读取 0 次**。
  按「分支必须能被某条真实路径走到两个方向」的判据，它该删。
  现在**真接上**：5xx / 429 / 异常 → 可重试；4xx 与「200 但 `ok !== true`」→ 不可重试。
  配套 `releaseBackfillKey` 把 key 从 `backfillDone` 放出来（原来只有 `add`/`has`，
  **没有 delete** → 失败一次即永久放弃）。
  **判据**：`grep '字段名:'` 数写入、`grep '.字段名'` 数读取。**读取 0 = 死字段。**

- **算了却没用上的中间量，是「即将静默写错」的信号**：
  `turn/end` 里算了 `scope` 塞进 `task.scope`，而 `runBackfillTask` **一次都没读它**，
  只传 `cwd`。`/log` 那侧是 `const cwd = typeof body.cwd === 'string' ? body.cwd : process.cwd()`。
  于是 `session?.header?.cwd` 为 null 时 → `process.cwd()` 是 **DSH 主进程工作目录**。
  实测：传 `{"cwd":null}` → 服务端返回 `scope = "desktop"`。
  **一条本该属于某项目的流水静默写进了另一个工作区** —— 写入成功、id 都有、日志全绿。
  **修法**：`/log` 已支持显式 `scope`，POST 时把它传上，`cwd` 保留作兜底。
  **判据**：算出一个值就传下去；传下去就有人读。中间断一环 = 数据写错地方。

- **「测试全绿」和「有测试守着」是两件事，而且报告里长得一样**：
  补记整块 8 个函数零覆盖，而当时回归 `TOTAL=73 FAIL=0`。
  已补三个脚本共 115 断言（详见 `docs/TESTING.md` 与地图 §3.7）。
  **判据**：`grep <关键词> _dbpreview/` 命中 0 = 零覆盖，
  没有「可能在别处测过」这种可能。
  ⚠️ **反过来也要查**：`verify-functions` 的「无新增死代码」**不覆盖箭头函数**，
  别把它当安全带。

- **重构换了「谁持有那个 id」，旧假设会静默失效**：
  子代理版补记 POST 的 sid 是**子会话**的，天然落在另一个键上；
  换成 `prepareCall` 直连后 sid 变成**主会话**的 → 补记落库那一刻会
  `turnActivity[sid].wroteLog = true` + `turnLogWrites[sid]++`。
  **补记越成功，越把下一轮的真实漏记判据毒掉**，全程无任何症状。
  **修法**：`/log` 收 `backfill: true` 时跳过记账（库里照写、诊断照留）。
  ⚠️ 这条**特别容易修过头**：拦截写成恒真会让**所有**写入都不记账 →
  每轮判「没写」→ 补记对每轮都触发。所以回归里必须有**反向守卫**
  （「正常写入必须照常记账」），只测「该拦的拦了」不够。

## ★ 2026-11-20 起撞到的 33 条（都「不报错」，按杀伤力排）

> 这一批的共同点：**测试全绿、日志干净、`node --check` 通过，但行为是错的**。
> 六条里有五条是「改了一端、另一端没接上」或「判据量错了字段」。

- **调试判据量错了字段，会产出看起来成立、实际错误的数字**（2026-11-20，最贵的一条）：
  `turn-未记流水` 的判据原来是 `record.writes > 0 && !record.wroteMemory`。
  而 `wroteMemory` 只在 `tools/result` 的 `file_path` 落在 **`store.root` 里面**时才置位 ——
  可写流水走的是**工作区脚本** `D:\workspace\...\.dsh-fatfishdream-memory\log.ps1`，
  `store.root` 是 `D:\dsh-fatfishdream-memory`，**永远不在同一棵树**。
  于是判据恒真：**只要本轮动过文件就必报「未记流水」**。
  实测当天 6 条全部假阳性，其中一条在 **7 秒前刚成功写入 id=1078**。准确率 0%。
  **规矩**：写任何诊断/统计判据之前，问一句 **「这个字段的值，和我要判断的那件事，是同一件事吗？」**
  答不上来就把候选量并排列出来看（本项目有四个语义相近的量：
  `writes` 动作 / `wroteMemory` 位置 / `wroteLog` 结果 / `logRouteHits` 尝试 —— 只有后两个问的是「记没记」）。
  **附加信号**：判据依赖的假设**曾经成立过**。`wroteMemory` 在「模型用 write 工具写文件」的年代
  是对的，写入通道换成 HTTP 之后它就静默失效了。
  **改通道 / 改存储位置 / 改调用方式之后，回头扫一遍所有依赖旧假设的判据。**

- **`exists()` 当判据 = 派生文件永不更新，且零日志**（2026-11-19 实踩，次日修）：
  `ensureWorkspaceScripts` 原本写 `if (await exists(scriptPath)) return false`。
  模板改了 → 已经生成过的工作区**永远拿不到新版**。
  实测：三个工作区的 `log.ps1` 全停在一天前（718 字节 vs 模板 1599 字节），
  新加的 `turnWrites` 输出**一次都没执行过**。
  **为什么特别难发现**：函数返回 `false` 兼作「没新建」，上层只在该值为 `true` 时打日志 →
  **「跳过了旧版本」在日志里一个字都没有**。
  **规矩**：凡是「模板 → 生成文件」的结构，判据必须比**内容**（`createHash('sha256')`），不能只比存在。
  **并且**：测试必须覆盖**产物**，不只是**生成器** —— 当晚我用临时脚本验了 13 条断言全绿，
  可测的是**源码里的函数**，磁盘上那份副本是旧的。

- **一个跨前后端的约定，只改一端等于没改**（2026-11-20 用户实报）：
  用户停用了一条规则，勾选「显示已停用的」看不到它。
  查出来：**后端 2026-11-16 就改好了**（`includeAll: q.get('status') === 'all'`，
  还配了一大段注释解释为什么不能靠传 `undefined`）；而前端只有「不勾」那一支
  （`if (!showInactive) params.set('status','active')`），勾选时**什么都不传** →
  后端回落 `active` → 停用条目永远列不出来。
  **为什么没有任何脚本抓到**：`audit-rules.mjs` 那条规则守的是**后端**（后端是对的，一直绿）；
  `selfcheck-full.mjs` 只核对依赖数组里**有没有** `showInactive`，不核对**它的值有没有被用上**。
  **两端各自的测试都绿，接缝是断的。**
  **规矩**：跨端约定的判据是「**有一端在测试里被验证过它真的传了**」，不是「字段存在」。
  最好写成**从两端各自抽出字面量再比对**（`frontAll === backAll`），
  而不是各写一个期望值 —— 后者在两边都改错时会一起通过。

- **注释里的代码不算代码**（2026-11-20，本月第二次踩）：
  修「显示已停用」时，我**故意把旧写法留在注释里作对照**：
  ```js
  //     if (!showInactive) params.set('status', 'active')     ← 讲解用
  if (showInactive) { params.set('status', 'all') }
  ```
  而新写的断言直接在原文上跑正则 → 「旧的写法已消失」**误报失败**，
  「前端发出的字面量」取到了注释里的 `'active'`，与后端 `'all'` 比对失败。**两条全是假红。**
  同月 2026-11-19 在 `writeUsesBlockRe` 上踩过一模一样的一次。

  **最能说明问题的是第三次**：写这条教训的当晚，我用 grep 核对
  「`ensureWorkspaceScripts` 的旧判据是否真的改了」，输出说
  **「⚠️ 旧判据还在 L1256」** —— 而 L1256 是**函数上方那段解释性注释**里的引用
  （`* 原实现是 \`if (await exists(scriptPath)) return false\``）。
  真实函数体里早就没有它了。剥掉注释再查才是 `false`。

  **判据**：断言前先剥注释（`stripLineComments()`），除非要断言的对象**就是**注释本身。
  **反过来说**：`grep` 命中不算证据 —— 尤其当你要证明的是「某段代码**不在了**」。
  验证「删除类」结论时，必须剥注释，否则**你查到的永远是你自己写的说明**。

- **从源码「截一段」来断言时，必须覆盖完整语法单元**（2026-11-20）：
  想断言 `turn-未记流水` 的条件里不许出现 `wroteMemory`，截法是「往上找最近一个含 `if (` 的行」。
  而修复后的条件是**多行**写法：
  ```js
  if (
    record !== undefined &&
    record.writes > 0 &&
    record.wroteLog !== true &&
    (logRouteHits.get(sessionKey) ?? 0) === 0
  ) {
  ```
  于是截到的是 `if (` —— **条件本体一个字都没进来**，
  结果「不许有 wroteMemory」和「必须有 wroteLog」两条**方向相反**的断言同时给出错误结论。
  **规矩**：切片要按括号配对取完整表达式，不能按「一行」取。
  **并且**：这个截取函数要被**自证段复用**，不能在自证里复刻一份 ——
  否则配对逻辑坏了，真实断言和自证会一起错，而自证还报告「通过」。

- **检测器本身有盲区，而且它不会告诉你**（2026-11-20）：
  `verify-functions` 的死代码检测里，`usageOf` 只跳过**定义那一行**。
  于是**在函数体内递归调用自己**的函数被算成「有引用」，
  `assertSupportedSchema`（外部零调用，真死代码）**一直躲过检测**，
  而脚本报「161 个符号已检查，无新增死代码」。
  **修法**：做括号配对得到函数体范围，落在范围内的引用记为「自递归」，不算外部调用。
  **附带的规矩**：修完盲区后要**在输出里打印覆盖边界**
  （本段只检查 `function` 声明，`const x = () => {}` 不在范围内），
  免得下一个人以为全查过了。这与文档里「§3.1 裸数字表」「§3.3 代码块」是同一类病。

- **端口每次启动都变**：脚本和指引必须读 `$env:DSH_WEB_URL`，不要写死。

- **断言里不许写字面量 `true`/`false`**（2026-11-15）：
  `check(name, true)` 永远通过 —— 断言在，测的东西不在。
  `_dbpreview/selfcheck-dir-name.mjs` 曾有一句
  `check('指针优先级最高，改常量不会移动已有安装', true)`，
  它声称验两件事，实际一件都没验（选址走了哪一级、指针有没有被读，一概不知）。
  这和历史上 `reportBudget` 静默失效两天是**同一种病**。
  **规矩**：
  - 分支内部的「已满足」也要写成**可失败的表达式**（如 `reason === 'pointer'`），
    不写 `true` —— 扫描器无法区分它和恒真断言；
  - **没有断言可写时就不要产生断言**，只 `console.log` 说明「本段不适用」。
    把一个恒假断言改成恒真断言，同样是假覆盖；
  - `check(name, false)` 只在「发现错误才失败」的守卫分支里合法
    （如 `if (seen.has(id)) check(...)`），别误删。
  **判据**：静态扫 `ok` 参数是字面量的调用，`true` 应为 0 处。
  **根因往往不在测试**：那次真正的病灶是 `/state` 的 `rootReason` 永远为空
  （`db-store.mjs` 没有该字段），拿不到证据才只能写 `true`。
  **遇到恒真断言先问「它缺什么数据」，别直接删。**

- **测「会改持久化状态」的接口前，必须先备份那个状态**（2026-11-16 两次实踩）：
  这条是上面那条的近亲 —— 两次都不是判断错，是**没料到那个接口真的会做事**。

  **第一次**：测 `/heartbeat`，直接对用户的真实 `policy.md` 发 POST，
  收尾语被改成「普通测试收尾语」。

  **第二次（更严重）**：测 `/root/move` 传 `"not-absolute"`，本意是验证
  「非法路径会被 400 拒绝」。结果它**真的执行了迁移** ——
  - 创建了 `D:\nonexistent-test` 并复制了整个记忆目录
  - 把 `cordis.patch.yml` 写成 `root: D:\nonexistent-test`
  - 把指针 `~/.dsh/memory-root.json` 指向新位置
  - 之后所有读写都进了那个新目录（包括我写的流水）

  恢复花了一轮：备份新位置 → `VACUUM INTO` 导回原位 → 改配置 → 改指针 → 删目录 → 重载。

  **规矩**：
  - 测写接口前，先 `Copy-Item` 备份**它会碰的所有持久化状态**。
    `/root/move` 碰三处：`cordis.patch.yml`（配置源）、`memory-root.json`（指针）、
    记忆目录本身。**只备份指针是不够的** —— 重载时插件重读的是配置文件。
  - **能改代码就别改数据**：这类接口优先用临时目录 + 直接调 `createStore` 测，
    不要对运行中的真实实例发请求。
  - 传「非法值」测试时，先确认**它真的会被拒绝**：
    `expandRoot` 用 `resolve()` 把相对路径补成绝对路径，
    所以 `isAbsolute(expandRoot(x))` 恒真 —— 我用一个「以为会被拒」的值去测，
    实际放行。**验证失败路径本身也要先验证**。
  - 出事后的恢复顺序：停插件 → 备份权威数据 → `VACUUM INTO` 导回 → 修配置 → 修指针 → 删残留 → 重载 → 核对条数。

- **写生产代码也要防「恒真/恒假分支」——不只是测试**（2026-11-16 第三次同病）：
  一个布尔变量若在「能继续往下走的所有路径上」都等于同一个值，读它的分支就是死代码。
  **写 `if (flag)` 前先问「有没有哪条路径能让它到这里是另一个值」**，答不出就删掉那个 flag。
  反方向同样成立：没在所有路径上赋值的变量可能是 `undefined`（恒假）。

  - 搬动 / 新增消费某变量的代码时，**先核对「定义行号 < 使用行号」**，
    不要只核缩进、不要只信 `node --check`；
  - 同源的还有 `let` 的「用了但还没赋值」（值是 `undefined` 而非期望值），
    这种连 TDZ 都不抛，**静默**。

- **`tool-recalc-map.mjs` 会把没改的行也整体重算**（2026-11-18 实踩）：
  改完 `index.js` 用它 `--write`，它把 `truncateBytes` 从 694 改成 753 ——
  可那段代码一个字都没动。原因是它按「符号在源码里的第几次出现」推位置，
  遇到同名变量 / 注释就会错。
  **改用** [`tool-sync-map-lines.mjs`](../_dbpreview/tool-sync-map-lines.mjs)：
  它**不自己算**，只从三个校验脚本的输出里读「声称 → 实际」，
  迭代到收敛（实测 2 轮）。判据是四个脚本全绿，不是「工具说改完了」。
  **记法**：**一个会改文件的工具，必须能证明它只改了该改的地方** ——
  拿 diff 对着看，别拿「它跑完了」当验收。

- **DSH 契约自相矛盾时，先加只读探针，别硬试**（2026-11-18 实踩）：
  C1-A 用 `session.append(..., {surfaceOp:{op:'replace'}})` 改已落库消息，
  被拒：`surface replace: sourceEventSeqs must include every shadowed surface node`。
  而 `official-session.md` 同时写着：
  - L361 / L370：`assistant/message` **禁止**携带 `sourceEventSeqs`
  - L339：replace 的节点 **必须**包含每一个被遮蔽节点

  **两条规则互斥**，按字面 `assistant/message` 的 replace 不可能成功。
  **规矩**：
  - 遇到这类矛盾**不要连着试**：每次试都要重载插件、花一整轮，而且
    `node --check` 与回归**都查不出**（它们不执行 DSH 的校验）；
  - 先加**只读探针**（只 `diag`、不 `append`），把现场打出来再判断；
  - 探针要写清「这条打出来之后，看什么字段、代表哪种结论」——
    否则拿到一堆数字还是不会判断。

  顺带一个反直觉的收获：那条修复**失败时是静默兜底的**（catch 住只记
  `[c1-hiccup-error]`，会话不中断）。这验证了「serial 事件里任何新代码
  必须包 try」这条规矩**是对的** —— 但它也意味着**失败很安静**，
  所以诊断项必须无条件写，不能只在成功时记。
