## 0. 先说最重要的：两个工作区的数字不可直接比较

这是整理时发现的第一个问题，也是**最容易误用的地方**。

### 两个判据不同，结果差 3 倍

| 判据 | 含义 | 本工作区实测 |
|---|---|---|
| **A. 宽松窗口**（SoftTest 用的） | 每条 user 之后 10 分钟内**存在**一条 logs | **92.1%** |
| **B. 严格 1:1** | 同上，但**一个 logs 只能算一次** | **83.8%** |
| **C. 按轮切分**（本工作区先前用的） | 按 `user-message → turn-stopping` 切轮，每轮是否有 logs | **56%** |

**为什么差这么多**：本工作区实测 **28/36 的相邻 user 间隔 ≤ 10 分钟**。
于是同一个 logs 会被算进多条 user 的窗口里 —— **判据 A 会系统性地高估覆盖率**。

> ⚠️ **所以「SoftTest 55.8%」与「本工作区 56%」的巧合不能当成互相印证** ——
> 它们用的判据不同（SoftTest 是 A，本工作区当时是 C）。
> 若要跨工作区比较，必须固定用同一个判据。

**建议统一用 B（严格 1:1）**：它既不放水，也不依赖 turn-stopping 事件的存在。

## 1. 两个工作区都验证成立的

### 1.1 漏记集中在「纯对话轮次」

| 证据 | 来源 |
|---|---|
| 漏记的 5 条连续出现，全是情感/反思/收尾/提问，无交付物 | SoftTest |
| 漏掉的 88 轮里，集中在「只给分析结论、没动文件」的类型 | 本工作区（按轮切分） |
| 有交付物的轮次几乎不漏 | 两边一致 |

### 1.2 「任务越难越容易忘」是错的

SoftTest 提供的反证（同一晚）：

```
漏记（低难度）：你是我可爱的大肥鱼 / 讨论漏记本身
没漏（高难度）：排 bug 技能需求说明（8 条硬约束）/ 扫代码 / 改代码
```

**方向相反**：高专注时反而记得写。

### 1.3 现有防护会「提醒一次就清零」

代码事实（本工作区，`index.js` L4497-4499）：

```js
if (delivered) {
  writeFailStreak.set(sessionKey, 0)   // ← 提醒后归零
}
```

后果循环：漏 2 轮 → 提醒 → 补 1 条 → 归零 → 再漏 2 轮。
**「漏」本身不产生累积后果。**

### 1.4 加提示词/加判据无效（已被多次证明）

| 判据 | 结果 |
|---|---|
| 「这条会让下个会话少走一次弯路吗」 | 只衡量技术价值 → 闲聊全漏 |
| 「纯寒暄、纯情绪交流不记」 | 给了自我说服空间 |
| 「等这批活收尾一起写」 | 听起来最负责任，实际漏得最多 |

本工作区 `AGENTS.md` 已有这条结论；SoftTest 独立得出同样判断（§3.6）。

## 2. 只有一边有的观察（待对方验证）

### 2.1 SoftTest 的「无意识遗漏」推论 —— 本工作区认为证据不足

SoftTest §1.5 的论证是：模型在分析漏记原因的那一轮自己也漏了，
所以「不是主动判断，是根本没意识到」。

**本工作区的异议**：那一轮恰好是**纯分析轮次**，正好符合「纯对话易漏」这条，
所以它同时支持两种解释，**不能区分**：

| 解释 | 预测 |
|---|---|
| 主动判断（觉得不重要） | 只在「觉得不重要」时漏 |
| 无意识遗漏 | 任何轮次都可能漏，与内容无关 |

**要区分这两者，需要的数据**：在**有交付物**的轮次里漏记的比例。
若接近 0 → 支持「按类型分层」；若显著大于 0 → 支持「无意识遗漏」。

**当前没有这个数据。**

### 2.2 本工作区发现的「命令长度不是变量」—— SoftTest 未涉及

| 工作区 | 用的命令 | 长度 |
|---|---|---|
| SoftTest | 六参数完整命令 | 长 |
| 本工作区（改动后） | 三参数短命令 | 短 |

两边漏记率**量级相同**（在各自判据下）。**这否定了「命令太长所以不写」这个假设。**

> ⚠️ 但受 §0 影响，这个对比**只能说明「没有数量级差异」**，
> 不能用来做精细比较。

## 4. 两个工作区一致的「下一步方向」

按两者独立得出的交集：

### 4.1 优先改「反馈结构」，不是「提示词」

两边都指向同一件事：**让「不写」有可累积的后果**，

具体候选（**尚未实施**）：

- 提醒后不清零，改为降 1（配合退避 2→4→8，避免太吵）
- 或：记录「本次会话累计漏了几轮」并写进诊断日志，让漏记**可度量**

### 4.2 改「完成点」的定义，而不是加要求

两个工作区都观察到：**有明确「要交东西」的轮次几乎不漏。**

推论（**待验证**）：问题不在「记不记得」，而在**纯对话轮次没有「完成」这个动作**，
于是「写流水」缺少可挂靠的时机。

候选：把「写流水」绑定到「回复用户之前」（回复是所有轮次的共同终点），
而不是「一轮结束」。

### 4.3 不要混入「目标漂移」

SoftTest 文档的第二部分（目标漂移）与漏记**病因不同、治法不同**：

| | 漏写 | 漂移 |
|---|---|---|
| 表现 | 少做了 | 做多了 / 做偏了 |
| 何时 | 纯对话 | 有交付物（越忙越容易） |
| 治法 | 加约束 | 加边界 |

**两者同时存在，但不要用同一个方案治。**
本工作区当前**只该关注漏记**，漂移另有 `AGENTS.md` 的纪律条款。

## 5. 复现命令（两边通用）

```powershell
$env:DSH_WEB_URL                      # 端口每次重启都变，必须读

# 流水（字段是 entries，不是 rows）
Invoke-RestMethod "$env:DSH_WEB_URL/api/dsh-memory/entries?table=logs&limit=500"

# 原文（字段是 rows，不是 entries）
Invoke-RestMethod "$env:DSH_WEB_URL/api/dsh-memory/archive?scope=<项目名>&limit=3000"
```

**严格 1:1 覆盖率算法**（推荐统一用这个）：

```js
const W = 10 * 60 * 1000
const logTs = logs.entries.map((r) => new Date(r.ts).getTime()).sort((a, b) => a - b)
const users = arch.rows
  .filter((r) => r.role === 'user')
  .map((r) => new Date(r.ts).getTime())
  .sort((a, b) => a - b)

const used = new Set()
let hit = 0
let miss = 0
for (const u of users) {
  const i = logTs.findIndex((t, idx) => !used.has(idx) && t >= u && t <= u + W)
  if (i >= 0) { used.add(i); hit++ } else miss++
}
console.log(`覆盖率 ${(hit / users.length * 100).toFixed(1)}%`)
```

## 6. 一句话

> **漏记不是「忘了」，也不是「太难」，而是「纯对话轮次没有完成点」。**
> 这个结论两个工作区独立指向同一处，但**尚未被验证** —— 验证方法是：
> 改「完成点」的定义（写流水绑定到回复前），观察严格 1:1 覆盖率是否上升。

**在此之前，不要为漏记改任何判据。**
