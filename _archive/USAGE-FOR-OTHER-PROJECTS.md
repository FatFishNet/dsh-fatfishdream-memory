# 大肥鱼的梦 · 记忆系统使用规范

**DeepSeek Harness 记忆插件 | 所有项目通用**

> ⚠️ **本文件已退役（2026-11-13）。**
>
> 原因：模型**不会主动读文件** —— 它不知道自己有这份文档，也没有理由去找。
> 真正会生效的是**每轮注入的内容**（约 1.2KB，写在 `index.js` 的 `usageLines` 里）。
>
> 本文件保留**仅供人查阅**：想了解记忆系统的完整设计、边界与演变过程时看这里。
> 模型侧的使用规范以注入为准，不以本文件为准。

最后更新：2026-11-13（存储层改 SQLite、单表拆四张表、fact 并入 pref、写入时机清单、检索改 FTS）

---

## 一、这是什么

装在所有项目上的长期记忆。每轮对话自动把相关结论带进上下文；
用户的情绪表达会被插件自动记录；**不再问用户"要不要记"** —— 由模型自己判断。

**模型不需要"打开"它，但需要知道怎么写入 —— 写错通道会静默失败。**

## 二、记忆存在哪

```
D:\FatFishDream-memory\
  memory.db                 ← 主存储（SQLite，四张表，所有记忆都在这里）
  policy.md                 行为规则（「给模型的规则」小节注入所有项目，不进数据库）
  state.json                项目登记表
  logs\YYYY-MM-DD.log       插件诊断日志
  _archive-md\              旧 .md 存储的归档（已迁入 memory.db，勿再读写）
```

**项目的作用域名跟着工作区目录名走。**
工作区是 `D:\workspace\ForzaOverlay`，记忆的 `scope` 就是 `ForzaOverlay`。

### 四张表（v2 拆表，2026-11-13）

| 表 | 装什么 | 会注入吗 | 量级 |
|---|---|---|---|
| `profile` | **用户画像**：关于用户这个人（称呼、喜好、处境、审美） | ✅ 每轮 | 极小 |
| `rules` | **规则与偏好**：分全局（`scope='__global__'`）与项目两种 | ✅ 按 scope | 小 |
| `emotion` | 用户情绪，插件自动录入 | ❌ | 中 |
| `logs` | 操作流水：做过什么、踩过什么坑 | ❌ 靠检索 | 大 |

**拆表的依据是「生命周期与访问方式」**，不是内容主题：画像是几乎不变的人工数据、
规则是偶尔改的项目约定、流水是只追加的大量记录 —— 四者的读写模式完全不同。

### `rules` 表的 kind（只有三种）

| kind | 含义 | 例子 |
|---|---|---|
| `redline` | 违反会出事 | 「不要注册工具」 |
| `pref` | 怎么做 | 「先给方案再改代码」 |
| `state` | 是什么 | 「这个项目是做 HUD 的」 |

> **原来的 `fact` 已并入 `pref`（2026-11-13）** —— 两者对系统行为毫无差别
> （注入排序、截断优先级、预算计算全一样），区分只增加判断负担。
> 实测当时 72 条 pref 里装的大多是技术约定，而 2 条 fact 反而是用户偏好，
> 说明这个分类在实操中是失败的。

### 注入的段落

| 注入段落 | 来源 |
|---|---|
| `## 全局结论` | `profile` 表 + `rules` 里 `scope='__global__'` 的规则 |
| `## 全局规则` | `policy.md` 的「给模型的规则」小节（**只能手工改**） |
| `## 项目结论` | `rules` 里本项目 scope 的规则 |
| `## 记忆索引` | **路由表现算**（`GROUP BY topic`），自动生成 |
| `## 记忆使用说明` | 插件代码里的固定文本 |

**注意 `## 记忆索引`**：它列出"记忆里有哪些主题、各多少条"。
看到似曾相识的问题，先按这里的主题关键词检索再动手 —— 不要凭空猜以前怎么解决的。

## 三、写入：只用标记，永远不要用 write / edit / pwsh 直写

### ⚠️ 为什么

记忆根目录 `D:\FatFishDream-memory` 在工作区**之外**。
用 `write` / `edit` 写它会被 DSH 的文件沙箱拒绝，或弹提权请求。

**更重要的是：主存储是 SQLite 数据库。**
用 `write` / `edit` 碰 `memory.db` 会**损坏数据库**，不是被拒那么简单。

**pwsh 直写也一样**：脚本操作 `memory.db` 同样是禁忌。改记忆走标记或 GUI。

**提权也解决不了**：给 profile 加 `additionalWritableRoots` 在 Windows 上
不受支持，会让 `pwsh` 全部瘫痪 —— 项目连 `dotnet build` 都跑不了。

### 三种标记

| 标记 | 落到哪 |
|---|---|
| `<!--mem-log-->` | `logs` 表（流水，当前项目） |
| `<!--mem-fact-->` | `profile` 表（用户画像，跨项目） |
| `<!--mem-note-->` | `rules` 表（项目规则，当前项目） |
| `<!--mem-fix-->` | 按正则软删全局规则（兼容旧用法） |

写在**回复正文**里，插件监听 `assistant/message` 自己入库。

```
<!--mem-log
- 做了什么 / 踩了什么坑 / 验证结果
-->
```

**不要自己写时间标题**，插件自动加时间戳。

## 四、画像 vs 规则：先分清「对人」还是「对事」

**这是最容易搞错的地方，也是选错标记的根源。**

| | 用户画像（`mem-fact` → profile 表） | 规则（`mem-note` → rules 表） |
|---|---|---|
| 回答什么 | 「用户这个人是什么样」 | 「AI 干活时怎么做」 |
| 例子 | 用户很穷，不希望浪费 token | 先给方案，确认后再改代码 |
| 判断法 | **需要主语「用户」才成立** | **本身就是一个动作** |

### 判断法：删掉主语后，句子还成立吗？

```
「用户很穷」     删主语 → 「很穷」  不成立 → 画像
「先给方案」     本来就是动作      成立   → 规则
```

### ⚠️ 拿不准时的默认值：记成项目级

因为「项目规则被误当全局」会在其他项目造成实际损害，
而「用户画像被记成项目」只是多记几份，没有危害。

**技术笔记永远放项目，不要放全局** —— 放全局会挤占所有项目的预算。

### 人称规范

**指用户写「用户」，指 AI 写「AI」；禁用「我」「你」。**

理由：记忆的写者和读者都是 AI，但 GUI 里看它的是用户。
中文的「我」依附于说话人，视角一混就读错 ——
「用户称呼我为大肥鱼」在用户眼里会变成「用户自己叫大肥鱼」。


| 满足 | 例子 | 去处 |
|---|---|---|
| ①+② 关于用户 | "用户不喜欢我长时间读源码钻研" | **全局** |
| ① 但②是软件知识 | "DSH 装插件要两步" | **项目** |
| 都不满足 | 具体项目的构建命令 | **项目** |

**一句话记法：全局只装「关于用户的事」，不装「关于软件的事」。**

> ⚠️ **拿不准时记成项目级，不要记全局。**
> 「项目规则被误当全局」会在其他项目里造成实际损害；
> 「全局偏好被记成项目」只是多记几份，没有危害。

### 第二级：约束 vs 经验

| 类型 | 判据 | 去处 |
|---|---|---|
| **约束** | 违反会导致具体后果（必须这样做） | `mem-note` → `kind='pref'`/`'redline'`，**每轮注入** |
| **经验** | 描述「曾经发生过什么」（踩坑过程、某次排查） | `mem-log` → **不注入**，检索取用 |

**判定一句话**：「以后必须遵守」→ 规则；「曾经发生过」→ 流水。

**为什么这样分**：项目段有 4096 字节预算、满了会截断，只能放小而稳的约束；
流水不注入、写多少都不撑爆。把经验写进规则会挤掉真正的约束，项目越久越挤。

## 五、什么时候记 —— 不必等改代码，也不必问用户

**满足任一条件就直接记，不要征求同意**（写操作提醒已取消，全靠你判断）：

1. **改了东西**：文件 / 配置 / 数据 → 记一条流水
2. **发现自己错了**：判断失误、走弯路、被用户纠正、反复改才对
   → 记流水，写清「错在哪、下次怎么避免」。**这条最容易被漏，也最值钱**
3. **发现更好的做法**：更快的方法、更省事的工具链、更好用的参数
   → 记流水。这类往往不改文件，但积累了才是效率的来源
4. **确立了项目规则**：某条约定以后每次都要遵守
   → 用 `mem-note` 记成规则，别记成流水
5. **用户给了重要反馈或偏好** → 关乎用户本人的用 `mem-fact`

**不必记**：纯问答、纯讨论、纯检索、闲聊。

> **判断标准：一年后回头看，这条能不能让你少走一次弯路？能就记。**

### 卡住的时候怎么办

如果同一处试了 **2~3 次仍不对**，**停下来**，不要继续装作有把握地反复改。

明确告诉用户「这里我找不到规律，需要你指个方向或提供参考」，
然后记一条流水说明「当时没有可靠依据」。

**这比记十条「我又错了」有用** —— 下次遇到同类任务，先找依据再动手。

## 六、检索历史：不要凭空猜测

**记忆库里积累了大量历史经验（`logs` 与 `emotion` 表），但它们不注入。**
遇到似曾相识的问题时，**先查，再动手**：

```
/memory search <关键词>
```

**中文按字匹配**：搜「沙箱」能命中含"沙"和"箱"的条目，不必完整词组。

> 实现方式：FTS5 的 `trigram` 要求查询词 ≥3 字符（「沙箱」搜不到），
> `unicode61` 对中文整段成词（同样搜不到）。只有「写入时把中文逐字空格分隔 +
> 检索时同样拆分用 AND 连接」两种语言都正常 —— 见 `db-schema.mjs` 的 `segmentCjk`。

查到后想看全文：

```
/memory show <id>
```

**典型该查的场景**：

- 遇到以前处理过的报错（构建失败、沙箱拒绝、编码问题）
- 做同类改造（改绘制代码、调配置、写文档）
- 觉得"这个坑我好像踩过"的时候

## 七、限额：写入无限，注入有预算

| 项 | 限制 |
|---|---|
| 库里能存多少 | **几乎无上限**（实测 5 万条约 17.8MB、检索仍 0.1ms） |
| 单次能写多少 | **无限制** |
| **每轮注入多少** | ✅ 画像 8000 / 规则 8000 / 项目 4096 字节 |

**注意：这是上限，不是固定开销。** 实际只按现有内容的字节数计费。

### ⚠️ 判断"会不会被截断"，看**注入字节**，不是文件字节

```
注入字节 = 过滤掉 stale/deleted 之后，实际注入的字节数
```

`stale`（停用）的条目**不注入但仍在库里**。所以：
- 注入超 80% → 该精简（合并同类、把过时条目标 stale）
- 看到「已截断」→ **内容没丢，仍在库里**，不要重复补写

### 超预算时的行为

超预算时会保留**头 40% + 尾 60%**，中间标记 `…（省略 N 条）…`。

**尾部的（最新写入的）一定保留** —— 旧实现从头截，导致最新的结论最先丢失。

## 八、全局规则与自动行为

### `## 全局规则` 段

来自 `policy.md` 的「给模型的规则」小节，**对所有项目生效**。
2026-11-13 已精简到 2 条（507 字节）：写记忆只能用标记、每轮收尾语。

**不能用标记改它**（只读），看到照做就行。

> **为什么 policy.md 不做成 GUI 宽文本编辑器**：它是插件运行规范，
> 改错会直接破坏插件功能（丢掉"只用标记"则收不到记忆）。
> 与可随手增删的偏好不同，它需要人看清楚再改，因此只允许手工编辑文件。
> 唯一例外是收尾语那一行 —— 受约束的单行输入（限 80 字节、自动合并多行），
> 改错后果小。

### 情绪自动录入

用户在对话里表达情绪时，插件自动入库（`emotion` 表，`writer='plugin'`），
不依赖模型判断、**不占注入预算**。

- 覆盖六个簇：夸赞、吐槽、爱意、友善、喜悦、低落
- 判定方式是情感词典打分 + 否定/程度/转折规则 + 反讽检测
- 只认真人消息，代码块/引号内被讨论的字样/URL 不计入
- **可能误判**：自动推断不应用作对用户性格的判断依据
- 误判可在 GUI 里删改，或用 `/memory review <id> retract`
- 条目带 `evidence` 字段（命中的词 + 得分），便于判断是否误判

## 十、格式规范

### 一条 = 一个结论，一行

```
- [active] 结论内容
```

- `[active]` / `status='active'`：生效中
- `[stale]` / `status='stale'`：已停用（可能过阵子再启用）
- `[superseded]`：被新条目取代
- `[deleted]`：软删除，可在 GUI 恢复

### ⚠️ 一条只说一件事

不要把「理由」和「规定」焊在一句里。
理由属于画像（`mem-fact`），规定属于规则（`mem-note`）。
这样改一边不动另一边，而且两边预算分开算。

### ⚠️ 自包含

每条要能独立看懂。避免"同上""见上一条"这类依赖上下文的写法。

## 十一、五条铁律

1. **只用标记写记忆**，不用 `write` / `edit` / `pwsh`（会损坏数据库）
2. **画像只装关于用户的事**，技术笔记放项目规则
3. **约束进规则、经验进流水**（"以后必须遵守" vs "曾经发生过"）
4. **拿不准记项目级**，不要记全局
5. **遇到似曾相识先检索**，不要凭空猜测

> 铁律 3 的「约束 vs 经验」是比「fact vs pref」更本质的分层：
> **规则会每轮注入、有 4096 字节预算；流水永不注入、按月分片、只追加。**
> 把经验写进规则会挤掉真正的约束，项目越久越挤 —— 那样只能反复精简或扩容，
> 治标不治本。判定一句话：「以后必须遵守」→ 规则；「曾经发生过」→ 流水。

## 十二、出问题怎么查

日志：`D:\FatFishDream-memory\logs\YYYY-MM-DD.log`

| 日志行 | 含义 |
|---|---|
| `[assistant-message] hasMarker:true` | 读到了回复里的标记 |
| `[mem-写流水] {"db":true}` | 写入成功（`db:true` 表示入了数据库） |
| `[mem-写入失败]` | 写入失败，后面写了原因 |
| `[db-FAILED]` | 记忆库打不开，已回退文件模式 |
| `[inject-db-FAILED]` | 读库失败 |
| `[turn-未记流水]` | **有写操作但没写记忆**（仅记录，不打扰） |
| `[entry-status]` / `[entry-deleted]` | GUI 里的停用 / 删除操作 |
| `[persona]` 相关 | 人称检查（写错不阻止保存） |
| 有 hasMarker 但无 `mem-写*` | 解析或写入出错，查上面那行 |
| 连 `[assistant-message]` 都没有 | 标记没写在正文里，或事件监听失效（需重启 DSH） |
