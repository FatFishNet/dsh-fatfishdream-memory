## 0. 先说最重要的：两个工作区的数字不可直接比较

这是整理时发现的第一个问题，也是**最容易误用的地方**。

### 两个判据不同，结果差 3 倍

| 判据 | 含义 | 本工作区实测 |
|---|---|---|
| **A. 宽松窗口**（SoftTest 用的） | 每条 user 之后 10 分钟内**存在**一条 logs | **92.1%** |
| **B. 严格 1:1** | 同上，但**一个 logs 只能算一次** | **83.8%** |
| **C. 按轮切分**（本工作区先前用的） | 按 `user-message → turn-stopping` 切轮，每轮是否有 logs | **56%** |

**为什么差这么多**：本工作区实测 **28/36 的相邻 user 间隔 ≤ 10 分钟**。
于是同一个 logs 会被算进多条 user 的窗口里 —— **判据 A 会系统性地高估覆盖率**。

> ⚠️ **所以「SoftTest 55.8%」与「本工作区 56%」的巧合不能当成互相印证** ——
> 它们用的判据不同（SoftTest 是 A，本工作区当时是 C）。
> 若要跨工作区比较，必须固定用同一个判据。

**建议统一用 B（严格 1:1）**：它既不放水，也不依赖 turn-stopping 事件的存在。

## 1. 两个工作区都验证成立的

### 1.1 漏记集中在「纯对话轮次」

| 证据 | 来源 |
|---|---|
| 漏记的 5 条连续出现，全是情感/反思/收尾/提问，无交付物 | SoftTest |
| 漏掉的 88 轮里，集中在「只给分析结论、没动文件」的类型 | 本工作区（按轮切分） |
| 有交付物的轮次几乎不漏 | 两边一致 |

### 1.2 「任务越难越容易忘」是错的

SoftTest 提供的反证（同一晚）：

```
漏记（低难度）：你是我可爱的大肥鱼 / 讨论漏记本身
没漏（高难度）：排 bug 技能需求说明（8 条硬约束）/ 扫代码 / 改代码
```

**方向相反**：高专注时反而记得写。

### 1.3 现有防护会「提醒一次就清零」

代码事实（本工作区，`index.js` L4497-4499）：

```js
if (delivered) {
  writeFailStreak.set(sessionKey, 0)   // ← 提醒后归零
}
```

后果循环：漏 2 轮 → 提醒 → 补 1 条 → 归零 → 再漏 2 轮。
**「漏」本身不产生累积后果。**

### 1.4 加提示词/加判据无效（已被多次证明）

| 判据 | 结果 |
|---|---|
| 「这条会让下个会话少走一次弯路吗」 | 只衡量技术价值 → 闲聊全漏 |
| 「纯寒暄、纯情绪交流不记」 | 给了自我说服空间 |
| 「等这批活收尾一起写」 | 听起来最负责任，实际漏得最多 |

本工作区 `AGENTS.md` 已有这条结论；SoftTest 独立得出同样判断（§3.6）。

## 4. 两个工作区一致的「下一步方向」

按两者独立得出的交集：

### 4.1 优先改「反馈结构」，不是「提示词」

两边都指向同一件事：**让「不写」有可累积的后果**，

具体候选（**尚未实施**）：

- 提醒后不清零，改为降 1（配合退避 2→4→8，避免太吵）
- 或：记录「本次会话累计漏了几轮」并写进诊断日志，让漏记**可度量**

### 4.2 改「完成点」的定义，而不是加要求

两个工作区都观察到：**有明确「要交东西」的轮次几乎不漏。**

推论（**待验证**）：问题不在「记不记得」，而在**纯对话轮次没有「完成」这个动作**，
于是「写流水」缺少可挂靠的时机。

候选：把「写流水」绑定到「回复用户之前」（回复是所有轮次的共同终点），
而不是「一轮结束」。

### 4.3 不要混入「目标漂移」

SoftTest 文档的第二部分（目标漂移）与漏记**病因不同、治法不同**：

| | 漏写 | 漂移 |
|---|---|---|
| 表现 | 少做了 | 做多了 / 做偏了 |
| 何时 | 纯对话 | 有交付物（越忙越容易） |
| 治法 | 加约束 | 加边界 |

**两者同时存在，但不要用同一个方案治。**
本工作区当前**只该关注漏记**，漂移另有 `AGENTS.md` 的纪律条款。

## 5. 复现命令（两边通用）

```powershell
$env:DSH_WEB_URL                      # 端口每次重启都变，必须读

# 流水（字段是 entries，不是 rows）
Invoke-RestMethod "$env:DSH_WEB_URL/api/dsh-memory/entries?table=logs&limit=500"

# 原文（字段是 rows，不是 entries）
Invoke-RestMethod "$env:DSH_WEB_URL/api/dsh-memory/archive?scope=<项目名>&limit=3000"
```

**严格 1:1 覆盖率算法**（推荐统一用这个）：

```js
const W = 10 * 60 * 1000
const logTs = logs.entries.map((r) => new Date(r.ts).getTime()).sort((a, b) => a - b)
const users = arch.rows
  .filter((r) => r.role === 'user')
  .map((r) => new Date(r.ts).getTime())
  .sort((a, b) => a - b)

const used = new Set()
let hit = 0
let miss = 0
for (const u of users) {
  const i = logTs.findIndex((t, idx) => !used.has(idx) && t >= u && t <= u + W)
  if (i >= 0) { used.add(i); hit++ } else miss++
}
console.log(`覆盖率 ${(hit / users.length * 100).toFixed(1)}%`)
```

## 7. 2026-11-17 晚：方向性的发现（**推翻了前六节的前提**）

前六节都在问「模型为什么忘」，答案都指向「改模型行为」——
换判据、改完成点、加反馈结构。**这一节说：那些都是在错的地基上盖楼。**

### 7.1 根因：插件丢掉了 DSH 已经给出的轮次编号

查 DSH 自身的 Event 契约（`cordis_inspect_query` → `host/Event`）得到：

```
agent/turn-stopping   serial   (payload: { agent, turn: number, signal })
  "The turn is about to close..."
  "Scope-filtered dispatch: agent-scoped listeners receive only that agent."
```

**DSH 明确提供了 `turn: number`，且按 agent 作用域分发、不跨会话串。**

而插件的现状（`index.js` L4432）：

```js
safeOn('agent/turn-stopping', async ({ agent }) => {   // ← 只解构 agent
  const sessionKey = String(agent.session.id)          // ← 用 sessionId 当轮次键
```

**`turn` 被直接丢弃了。** 于是：

| 后果 | 机理 |
|---|---|
| 同一轮写 3 条 → 只算「写了」 | `turnActivity` 以 `sessionId` 为键，一轮内多次写被合并成同一个 `true` |
| 重记完全不可见 | 没有 `turn`，无法判断「这两次是不是同一轮」 |
| 漏记只能靠 streak 累加 | 因为不知道轮次号，只能数「连续几轮没写」 |

**这不是模型判断力问题，是插件丢了一个本来就拿到的字段。**

### 7.2 实测证据：`logRouteHits` 已经能数出「写了 3 次」，但数不出「是不是同一轮」

```json
{"streak":0,"wroteThisTurn":true,"logRouteHits":3,"writes":0,"turnMs":null}
   ↑ 05:53:52 —— 我因误判 system-reminder 在一轮内写了 3 条
```

`logRouteHits=3` 说明插件**看得见**调了 3 次。但它无法区分「一轮 3 次」和「三轮各 1 次」——
**缺的正是 `turn`**。有了 `(sessionId, turn)` 作为唯一键，两者立刻可分辨。

### 7.3 因此：**真正的方向是走 DSH 自己的事件，不是继续调判据**

> **用户 2026-11-17 的判断（重要）：**
> 「我们之前的方向都错了，走 DSH 客户端自己的路就可以完成所有的事情，只是之前没意识到。」

这不是猜测，是查证过的。DSH 的「白板」设计恰恰意味着**它把完整的扩展点都暴露了**，
缺的只是「去查它有什么」这一步。可用的现成信号：

| 事件 | 模式 | 给了什么 |
|---|---|---|
| `agent/turn-stopping` | serial | `turn: number` —— **精确轮次终点** |
| `agent/inbox/claimed` | emit | `turn: number` —— **轮次起点** |
| `agent/status` | emit | `idle ⇄ running` |
| `agent/pre-step` | waterfall | `turn` / `step`，还能拒掉这一步 |

**所以插件不必再自己猜轮次。** 现在这套「用 `session/event` 推测用户说了话、
再用 `sessionId` 攒计数器」的做法，是在没有轮次编号的情况下发明的替代方案 ——
**替代方案有了真品之后就该退役。**

### 7.4 一个必须写清楚的限制（否则会许下做不到的承诺）

`turn-stopping` **不能**让模型「想起来写流水」：

- 它在**轮次即将关闭时**触发，那时模型**已经答完**
- 它能做的是：**准确判定**这一轮写了没有、写了几个
- 它不能做的是：**在我按下发送之前拦住我**

所以两件事必须分开：

| 目标 | 手段 | 性质 |
|---|---|---|
| 让模型别忘 | 改注入文案（`usageLines`） | **行为层**，靠模型自觉 |
| 准确统计 + 抓住重记 | 插件订阅 `turn`，用 `(sessionId, turn)` 去重 | **机制层**，靠代码保证 |

**机制层能做到 100%；行为层永远做不到。** 不要用机制层的发现去宣称行为层已解决。

### 7.5 今天新发现的漏记形态：以「等你确认」结尾的轮次

补充 §1.1 的类型清单。实测 2026-11-17：

| 时刻 | writes | 结尾方式 | 写了吗 |
|---|---|---|---|
| 06:17:32 | 5 | 报告结果 + 给结论 | ✅ |
| 06:18:27 | 5 | **「你点头我就做」** | ❌ |
| 06:19:51 | 3 | **「你想先动哪块」** | ❌ |

**同样是 `writes=5`，一轮记住了、一轮没记住** —— 所以「工作量」不是变量。

**变量是结尾形态**：以「等你拍板 / 等你确认」收束的轮次容易漏。
机理：这类轮次**看起来像「话还没说完」**，实际已经结束（我发完就轮到用户了）。
这与 §4.2 的「缺少完成点」同源，但更具体 —— **「等你决定」被误当成「还没完成」**。

### 7.6 已修正的错误结论（自省）
