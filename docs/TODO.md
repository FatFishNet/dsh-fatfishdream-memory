`text` 是四张表共用的列（GUI 列表、`getById`、`/entries` 都读它），

### 修了什么

`index.js` 的 `session/event` 监听里，去重键原来是：

```js
const messageId = `${payload.turn ?? '?'}:${payload.step ?? '?'}`
```

`handledMessageIds` 是 apply 级**全局** Set，键不含 sessionId →
两个不同会话的同一 `turn:step` 互相压制。被撞的那条**既不进 archive
（原文永久丢失）、也不解析标记**，且无任何日志。

第 7 轮实测：全库 2858 条 assistant 只有 1884 个不同键；两个会话的 step
集合交集为空，其中一个会话的 assistant **一行都没有**。

已改成：

```js
const sid = session?.id === undefined || session.id === null ? '?' : String(session.id)
const messageId = `${sid}:${payload.turn ?? '?'}:${payload.step ?? '?'}`
```

### 为什么测不到

黑盒验证需要「**两个会话并发产生相同的 turn:step**」，而：

- 脚本无法伪造 `session/event` 事件 —— 那是宿主在真实对话中派发的
- 单会话测试里 `sid` 恒定，加与不加前缀的**行为完全一样**，
  这种测试会绿，但它**证明不了修复有效**（典型的假覆盖）
- 要真验，得开两个会话、在两边控制 turn/step 撞车，成本高且不可靠

### 当前只验到什么程度

### 附带风险（同一次改动引入，一并记着）

键空间变大 → 达到 500 上限更快 → 老键更早被淘汰。

淘汰是 **FIFO 不是 LRU**（`Set.values().next().value` 取最早插入的）。
若某键已被淘汰、又发生事件重放，同一条消息会被**再存一遍**，
archive 层产生重复行。这是既有设计，不是本次引入，但加 sid 让它更容易发生。

真要修得改成 LRU 或按 session 分组淘汰 —— 那是另一批活。
