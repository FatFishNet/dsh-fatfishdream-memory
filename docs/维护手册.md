## 1. 标记擦除器（`client.js`）

正文里的 `mem-log` 标记在界面上是**被 DOM 擦掉的**，不是渲染器隐藏的。
**看到标记 ≠ 记忆没写进去** —— 插件读的是 session 事件原文，与显示层解耦。

为什么走这条路（2026-11-13 调研，别再重踩）：链接引用定义会退化成可见段落；
`conversation.chat.node` 的视图组件是 ui-chat 私有、拿不到；
`MarkdownText` 导出表被 `Object.freeze` 冻结。所以只能事后擦。

**改动纪律**（每条都踩过）：

- **流式期间不要碰 DOM**（2026-11-14 第五代）：只在「最后一次带标记的变化之后
  安静 `QUIET_MS = 400ms`」才全量扫一次；页面一直变则最多 `MAX_DEFER_MS = 3s`
  强制扫一次。
  **为什么**：擦除必然改变高度（少几行文本）。在 React 正在写的那块 DOM 上反复擦，
  高度就来回变 —— 表现为**整个对话区在抖、滚动条跳**。
  前四代（跨段正则 / `display:none` 包半截 / `el.remove()` / 打 data 属性 + CSS）
  全在「让改动更隐蔽」上打补丁，方向是错的：**病根是时机，不是隐蔽度**。
  代价是流式时末尾几行标记短暂可见，结束后一次擦净 —— 高度只跳一次。
  **2026-11-14 用户已拍板接受这个取舍**（原话：「可以，就现在这样」）：
  每次回复末尾塌一次（约 0.2s）是**可接受的**，不要再为它引入：
  ① 擦成等长空白（会永久留一块空白）；② FLIP 平滑塌陷（要在 React 节点上写内联样式，
  和前三代翻车的是同一类操作）。真要动，先回头确认用户还愿不愿意换。
- **⚠️ 第六代（2026-11-16）：完整标记必须同步快擦，不要只排队。**
  用户报「每次切会话的时候 会一闪而过」——「每次」而非偶发，说明是确定性代码路径。
  **根因**：`MutationObserver` 回调是**微任务**，本应在浏览器绘制之前跑完；
  但第五代的回调只做 `schedule()` → `setTimeout(400ms)`，等于**主动把擦除推迟到
  绘制之后**。切会话时 React 重新挂载整段历史（实测 34 条已闭合标记），那一帧
  画出来就是原文。
  **修法**：按「会不会再变」切分 ——

  | 标记形态 | 会不会再变 | 处理 |
  |---|---|---|
  | 流式中 `<!--mem-log topic=x`（无 `-->`） | 会，还在长 | 保持 400ms 延迟**不动** |
  | 历史中 `<!--mem-log … -->`（已闭合） | 不会 | **同步 `fastStrip()` 立刻擦** |

  实现：`stripMemMarkers(root, {skipPartial:true})` 只处理完整标记；
  `addedNodes` 命中 `hasCompleteMarker()` 时同步调 `fastStrip()`。
  **`skipPartial` 默认 `false`，不传就是第五代原行为** —— 别把它改成默认 true，
  否则未闭合的标记也会被同步擦，第四代抖动会回来
  （`scrubber-faststrip-partial` 变异就是守这条的）。
  **不要因为「回调已经是微任务了」就以为万事大吉**：切会话是大量连续提交，
  绘制可能插在中间。完整标记同步擦能把窗口压到最小，但**历史消息里若仍有标记，
  就还有理论上的闪**（见下一条）。
- **历史消息里的标记是清不掉的，只能靠新消息不再产生。**
  2026-11-16 实测：archive 里有 51 条 06:15 之前的 assistant 消息带完整标记。
  它们每次切会话都会被重新渲染、再被擦一次 —— 所以「旧会话偶尔还闪」是预期内的，
  **不是回归**。要根治只能改 archive（会破坏「原文一条不落」的承诺），
  用户 2026-11-16 决定不做（原话：「没事了 新消息可以用就行」）。
  判断「闪烁是变好了还是变差了」时，**先区分是旧消息还是新消息**。 
- **扫描必须全量扫 `document.body`**。不要改回「只处理 mutation 记下的节点」——
  React 流式渲染会重建文本节点，缓存引用已脱离文档（`isConnected === false`），
  表现为「首屏擦得到、新回复擦不到」。
- **排队必须只认「这批变化里含 `<!--mem-`」**。页面平时一直在变（计时器、状态栏、光标），
  无条件排队会不停重置静止计时，「安静」永远等不到 —— 那就退回第四代了。
- **扫完调 `observer.takeRecords()`** 丢掉自写 mutation，否则刚擦完又排一轮。
- **防自激不能用布尔标志**：MutationObserver 回调是**异步**的，
  在 flush 里置位再复位，回调真正跑时读不到。现在用「静止计时」天然解决。
- **不要用 `display:none` 藏半截标记** —— DOM 不会把内容从隐藏壳里拿出来，
  会永久丢内容。正确做法是直接擦。

排查不要靠用户开 DevTools：应当走 `/api/dsh-memory/client-report` 回传 +
`diag('client-scrubber', ...)` 写进服务端日志，模型自己能读。

> **2026-11-16 更新：这条路现在是通的。**
> `fastStrip()` 每次真擦到东西都会回传
> `client-dom-report {"n":1,"fastStripped":N,"total":M}`（必须带 `dom=1`，
> 否则 `/client-report` 不解析 `detail`）。
> **判据**：用户切几次会话后看 `fastStripped` 涨没涨 ——
> 涨了说明快擦在工作；恒为 0 说明 `MutationObserver` 没拿到完整标记节点，得换方向查。
> 补它见 [`TODO.md`](TODO.md)。

### 1.1 ⚠️ 全局样式外溢：`data-dsh-mem-blank` 曾打断别的面板滚动（2026-11-15）

**症状**：用户报「每次改动功能，全局 skills 的滚动条都失效」。

**根因**：擦除器给「擦完只剩空白」的元素打 `data-dsh-mem-blank`，
而配套 CSS 注入在 `document.head`、**永不撤除**：

```css
[data-dsh-mem-blank] { display: none !important; }
```

旧判据只有 `el !== document.body`，等于「除 body 外全都可以隐藏」。于是：

```
滚动容器 A（overflow: auto）
  └─ 子元素 B 被擦成空 → 打标记 → display: none
     → A 的 scrollHeight 塌成 0 → 滚动条消失
```

`!important` 让它无法被别的样式覆盖回来。

**为什么「改功能才犯」**：只有出现 `<!--mem-` 文本时才会触发擦除。
写 `mem-log` 标记越频繁，撞上滚动容器的概率越高。

**修法**：打标记前加 `isSafeToCollapse(el)` 守卫，三道保守拒绝：

| 守卫 | 理由 |
|---|---|
① tag 白名单（`P`/`SPAN`/`DIV`/`BR`/`CODE`/`EM`/`STRONG`/`LI`） | `main`/`section`/`ul`/`table`/`nav` 是布局骨架，不是「文字空壳」 |
② **祖先里有 `overflow: auto/scroll` 就拒绝** | 这是本次事故的直接防线 |
②b **祖先被限高（`max-height`/`height`）+ `overflow: hidden` 也拒绝** | 不是所有裁剪都靠 `overflow:auto`；限高容器内显隐同样改变可见区 |
③ 高度 > 4px 就拒绝 | 被 flex/grid 撑开的空 div 是布局占位 |

**为什么用白名单而不是黑名单**：黑名单永远列不全；白名单漏掉一个只是
「少隐藏一个空行」（视觉上无害），方向是安全的。

**⚠️ 高度和宽度不能用同一阈值**：行内 `<span>` 只含空白时高度约 2px、
但宽度可能几十像素。若按宽度也卡 4px，正常的空 span 全被拒，
逐行收拢功能等于失效。这条是 `selfcheck-collapse-guard.mjs` 验证时发现的。

**回归守卫**：`selfcheck-dom-strip.mjs` §6（源码级 5 条断言）+
`selfcheck-collapse-guard.mjs`（**18 条**行为断言，用 DOM 替身真跑判据，
含「普通祖先不应误伤」的反向用例）。

> **通用教训**：往 `document.head` 注入带 `!important` 的全局 CSS 前，
> 先想清楚「它能命中的最坏情况」。插件共享同一页 DOM，任何全局规则
> 都可能打到别的面板上，而且**不报错、不崩溃，只是悄悄坏掉**。

## 2. 标记通道的细节（语法核心在 `AGENTS.md`，这里只记为什么）

**没有开闭配对**：一个 `-->` 就收尾。

**三条禁令**（每条都实际踩过，`node --check` 查不出来）：

| 禁止 | 会发生什么 |
|---|---|
| 写 `<!--/mem-log-->` 这类闭合标签 | 它不会被剥离，变成正文**永久写进库并每轮注入** |
| 开标签自带 `-->` 后再加闭合标签 | 同上 |
| 整条压成一行 `<!--mem-log topic=x 正文 -->` | **正则匹配不上，整条静默丢失，无任何报错** |

收尾的 `-->` 必须**单独起一行**。正文里要提到标记字样就拆开写
（反引号包住也不行 —— 解析器看原文，不看渲染结果）。

**topic 必须是 14 类之一，且独占标记行**。`topic=` 后面**换行**再写正文 ——
如果 topic 和正文挤在同一行，正文会被当成 topic 的一部分，不在白名单就被
`sanitizeTopic` 拒收、整条静默丢弃（诊断日志查 `[topic-rejected]`，
2026-11-14 实踩两次）。topic 本身写整句描述也一样被拒。

**文本位置**：`assistant/message` 在 `event.data.message.content`，
比 `user/message` 多一层。写错过一次，标记全不落盘且无报错。

**自检**：`_dbpreview/test-marker-forms.mjs` 用真实正则跑七种写法（含「参数顺序写反」）。
改过解析逻辑后先跑它。

## 3. 已知行为与坑（完整版）

**升级 DSH 后先看日志的 `health-check-verdict`**，确认「通过：10 项全部就位」
再谈功能验证。日志在 `D:\dsh-fatfishdream-memory\logs\YYYY-MM-DD.log`。

**依赖面**：9 个接口（`systemPrompt.context` / `commands` / `webServer` /
5 个事件监听 / `slots` / `node:sqlite`）。client 侧的
`sidebar.panellist` + `main` 是最高风险点 —— 若 DSH 改 slot 体系面板会消失，
但**记忆读写不受影响**。

**中文检索**：`trigram` 要求 ≥3 字符（「沙箱」搜不到），`unicode61`
对中文整段成词。只有「逐字分词 + unicode61」两种语言都正常 ——
见 `db-schema.mjs` 的 `segmentCjk`。

**contentless FTS 表不能 `DELETE`**：五张 `*_fts` 都是 `content=''`，
必须用 `'delete'` 命令并带原值，否则抛
`cannot DELETE from contentless fts5 table`。
（`archive_fts` 只有 2 列 `text, seg`，写 `'delete'` 时别照抄 logs 那 5 个值。）

**原文归档（`archive`，v4）**：写不进去是**静默**的 —— 模型照常回复、流水照常落库，
只是原文层空了。排查顺序：日志有没有 `[archive-user]` / `[archive-assistant]`
→ 没有就找 `[archive-write-failed]` → 再查 `archive_fts` 与表是否同条数
（`selfcheck-full` 的 C 段会比对）。**归档位置不能挪**：user 侧必须在情绪形态闸门之前，
assistant 侧必须在 `hasMarker` 判断之前。

**流水（`logs`）允许为空**：用户会清空记忆流水（2026-11-14 彻底删过一次）。
清空后注入里「记忆索引」只剩 `rules` 的 topic 计数，这是正常状态，不是故障。
清空流程见 `docs/TESTING.md` §10.2；依赖流水的测试必须自带种子或显式跳过，
不要因为 `logs=0` 就判失败。

**热重载后 `session/event` 可能失效**（日志不再出现 `[user-message]`）。
不是必然，遇到时完整重启 DSH。

**DSH 更新后插件消失，先查 junction 指向**：node_modules 重建会按注册源还原
junction，项目搬过家就会被指回旧路径。一行定位：
`Get-Item <node_modules>\dsh-fatfishdream-memory -Force | Select Target`。
指向不存在就 `rmdir` + `mklink /J` 重建，再 `set_bundle` 启用（2026-11-14 实踩）。

**`client.js` 是浏览器模块**，改完必须**完整重启客户端** ——
禁用→启用插件不会刷新浏览器里那份代码（只对 `index.js` 有效）。
搞错的表现是「代码改了行为没变」，极易误判成逻辑错。

**端口每次启动都变**。脚本和指引必须读 `$env:DSH_WEB_URL`，不要写死。

**本机 `node` 不在 PATH**。用 Electron 主程序代替：

```powershell
$env:ELECTRON_RUN_AS_NODE = 1
& $env:DSH_NODE_EXECUTABLE _dbpreview\verify-map.mjs
```

**⚠️ 临时脚本可能「写了但 node 读不到」（2026-11-14 实踩两次）。**
现象：pwsh 里 `Set-Content` 写完，`Test-Path` 返回 `True`，
同一秒 `& $env:DSH_NODE_EXECUTABLE xxx.mjs` 却报 `MODULE_NOT_FOUND`；
部分文件过一会儿会自己消失。用 `write` 工具写的文件**一直正常**。

- 排查脚本优先用 `write` 工具落盘，不要用 `Set-Content` 临时造文件；
- 一次性脚本放**工作区根目录**（不要放 `_dbpreview/`），跑完立刻删；
- 实在要临时造文件，先 `node -e "console.log(1)"` 验一下通道是否正常。

这不是插件的问题，是写通道的时序/沙箱问题 —— 但会让人误判成「脚本语法错」。

### 3.1 ⚠️ 改 `SCHEMA_VERSION` 时，迁移会跑在你备份之前（2026-11-14 实踩）

**这是本项目最危险的一类时序陷阱。** 现象：

1. 你改完 `db-schema.mjs`，把 `SCHEMA_VERSION` 从 N 提到 N+1；
2. **HMR 立刻把新代码装进正在运行的插件**（这一步不写 `[apply-start]` 日志，所以看不出来）；
3. 插件下一次 `open()` 就自动跑迁移 —— 真实库在你做任何事之前就已经变了；
4. 你这时才去 `backup-db.mjs`，拿到的是**迁移之后**的库，**不能当回退点**。

2026-11-14 实测：备份文件名写着 `before-v5`，打开一看 `user_version=5`、
`entries` 已删 —— 完全失去了回退价值。

### 正确顺序（不可调换）

```
① 备份真实库          ← 此时 SCHEMA_VERSION 还是旧的
② 改 db-schema.mjs（升版本 + 写迁移）
③ 干跑：拿 ① 的副本跑 openMemoryDb，验证通过
④ 才让真实库迁移（HMR 或重载都会触发）
```

**反例（做错了会怎样）**：先改代码再备份 → 备份是迁移后状态 →
真出问题只能退回更早的备份，丢掉这段时间的新数据。

### 备份脚本自身的坑

`_dbpreview/backup-db.mjs` 用 `new DatabaseSync(src)`（**读写**打开，
没加 `readOnly`）。对已经迁移过的库它不会造成额外变化，但**它自己也会触发
`openMemoryDb` 之外的隐式行为** —— 备份前请确认插件没有在跑：
最稳的是先禁用插件，备份，再改代码。

> 判断「这份备份能不能当回退点」的唯一方法：打开它查 `PRAGMA user_version`，
> **必须等于你打算回退到的那个版本**。文件名不可信。

## 4. 怎么改这个项目（完整流程）

**0. 动手前先读 [`docs/项目地图.md`](项目地图.md)。**
它是结构索引（函数在哪、谁调谁、改哪影响什么）。
不知道"改这个会波及哪里"就开始改，是这个项目最常见的返工原因。

### 标准流程

1. 读地图 —— 找到要改的函数，确认 §9 里的影响面
2. 备份 `index.js`（硬约束 6）：`Copy-Item index.js index.js.pre-<改动名>`
3. 改代码
4. `node --check`
5. 改 schema 时按硬约束 7 走
6. 跑 `_dbpreview/` 的回归（清单见 [`TESTING.md`](TESTING.md)）
7. 重载插件（禁用→启用）或重启 DSH
8. 看日志确认加载正常

> ⚠️ **改 `SCHEMA_VERSION` 时顺序要改**：先备份、再改代码（见 §3.1）。
> 否则迁移会被 HMR 提前触发，备份失去回退价值。

### 4.1 ⚠️ 「只改名字」的批量替换：先分类，再动手

**2026-11-14：改目录名 `dsh-memory` → `dsh-fatfishdream-memory`。**

`dsh-memory` 这个名字在本项目里同时承担四个角色，**只有一个该改**：

| 角色 | 例子 | 改不改 | 改了会怎样 |
|---|---|---|---|
| **目录名** | `dsh-memory/index.js` | ✅ 改 | — |
| **HTTP 命名空间** | `/api/dsh-memory/search` | ❌ 不改 | 126 处，硬约束 17 已明说 |
| **slot id** | `id: 'dsh-memory'` / `key: 'dsh-memory'` | ❌ 不改 | **侧边栏注册失效，面板消失** |
| **entryId / patch id** | `include:dsh-memory` / `- id: dsh-memory` | ❌ 不改 | **插件装不上** |
| **日志前缀 / effect 标签** | `[dsh-memory]` / `'dsh-memory: xxx'` | ❌ 不改 | grep 习惯全变，无收益 |

**实际执行**：78 处路径替换（69 处直接引用 + 9 处 `../dsh-memory/` 相对路径）。

**两条硬规矩**：

1. **干跑要看「分类」不看「命中数」。**
   第一次干跑报「69 处」，数字看着合理，但我没逐类核对 ——
   而规则里 `id: 'dsh-memory'` 会被改成 `id: 'dsh-fatfishdream-memory'`。
   是检查 `client.js` 时才发现，加了标识符白名单才真跑。
   **命中数对了不代表改对了对象。**

2. **相对路径是独立的一类，别指望一条正则全包。**
   第一版正则排除了 `/api/` 前缀，结果连 `../dsh-memory/` 里的 `/` 也被当成前缀跳过了，
   漏了 9 处，5 个测试脚本 `ERR_MODULE_NOT_FOUND`。补跑一遍才清。

**改完必须做的三件事**：

```
① rmdir + mklink /J 重建 junction（指向新目录）
② 禁用→启用插件（看到 entryId 仍是 include:dsh-memory 是正常的）
③ 跑全量回归（`_dbpreview\run-all.mjs`，脚本清单只在它的 `SCRIPTS` 里维护）
```

> 关于包内的 README 与 STORAGE：
> 2026-11-14 它们不在包内，是**用户主动删除**的（打算重写），
> 不是改名过程丢的。排查时若 `verify-doc-links` 报
> 「文档本身不存在: 包内 README」，先确认是不是有人故意删了，
> 别急着从回收站捞 —— 那会覆盖用户的决定。

**`verify-doc-links.mjs` 的一个盲区**：它核对「文档里引用的文件是否真存在」，
但**对它自己那份待查文件清单不设防** —— 清单里的文件被删了，
它只报「文档本身不存在」。看到这类报错先 `Get-ChildItem` 确认文件在不在，
再判断是「文档写错了」还是「文件真的没了」。

### 4.2 ⓘ 只读沙箱下查记忆会看到中文乱码 —— **不要修，不是我们的问题**

**现象**：权限为 `read-only` 时，用 pwsh / node 读 `/api/dsh-memory/*` 的中文字段，
模型看到的是 `能 ` 这类乱码。同一时刻把权限切到 `workspace-write`，一切正常。

**机制**（2026-11-14 查证）：

```
HTTP 响应 UTF-8 → 解码成 .NET string（码点正确，如 干=24178）
  → 写 stdout 时按 [Console]::OutputEncoding 编码
  → 该值来自代码页 936(GBK)
  → 模型收到错误字节
```

修它需要 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`，
而这属于 .NET 静态调用，**在只读沙箱的 ConstrainedLanguage 模式下被禁**
（报错原文：`Method invocation is supported only on core types`）。
workspace-write 是 FullLanguage，所以正常。

**判断：这是 DSH 沙箱模式的行为，不是记忆插件的缺陷，也不需要修。**

用户 2026-11-14 原话：「这个其实不算问题，真正用这份记忆系统工作的人不会用这个权限」。

**理由**：记忆系统的正常使用本来就要写库（标记入库、情绪入库、GUI 编辑），
只读权限下它只能被读、不能被用，那是审计场景不是使用场景。
为了一个「非使用场景」去改插件的路由或编码，只会扩大出错面。

**只读权限下真要查，用这两条**（都不需要改代码）：

1. **只取 ASCII 字段定位**：`id` / `role` / `ts` / `len` / `total` 不受影响，
   足够回答「什么时候、谁、多少条」；需要正文时再说。
2. **申请一次 `workspace-write`**：中文立刻正常，已验证。

> ⚠️ 顺带记一个**不同的**限制，别和上面混为一谈：
> 沙箱下 `& $node -e "..."` 的子进程 stdout **捕获为空**（取回 `[]`），
> 那是命名管道 / `stdio: 'pipe'` 的 EPERM 限制，**与编码无关**。
> 遇到它别去调编码，调了也没用。
>
> **它的后果比「捕获为空」严重得多（2026-11-15 补记）**：
> `_dbpreview/run-all.mjs` 曾因此报出 **`TOTAL=32 FAIL=32`、每个都 `exit=-1`**，
> 而同一时刻用 pwsh `foreach` 循环跑是 **32/32 全绿**。
> 成因是旧代码 `const code = r.status ?? -1` —— 把「一个都没跑起来」
> 算成了「32 个全部失败」。
>
> **记法**：看到「全部脚本同一形态失败、且 note 空白」，先怀疑是捕获层而不是代码。
> 现在 `run-all.mjs` 走 `lib-spawn-capture.mjs`，会自动降级到临时文件捕获，
> 受限权限下也能正常跑。**别再用 `r.status ?? -1` 吃掉「没启动」这个状态。**

### 4.3 ⓘ 日志时间断档 ≠ 故障，先查是不是关机

**2026-11-14 实测案例**：11-13 的日志最后一条在本地 15:53，
11-14 的第一条在次日 00:43，中间空了 **8 小时 50 分**。

当时怀疑是插件丢日志 / 监听失效。**实际原因是电脑关机了两天才开。**

**判据（三条都对上就是正常关机，不是 bug）**：

| 检查点 | 正常关机 | 真异常 |
|---|---|---|
| 断档前最后一行 | 完整的 `[turn-未记流水]` 或 `[user-message]` | `[xxx-FAILED]` / 抛错栈 |
| 断档后第一条 | `[apply-start]` | 有内容但没有 `apply-start` |
| 断档期间 | 什么都没有 | 有零星记录但时间不连续 |

**为什么插件不可能「丢」日志**：它是**被动监听** `session/event` 的。
DSH 进程不在，事件就不存在，日志自然是空的 —— 这是物理事实，不是数据损坏。

**别做的事**：

- ❌ 别去翻 `logs/` 找「丢失的记录」—— 关机期间本来就没有事件
- ❌ 别怀疑 `diag()` 写盘失败 —— 下一轮对话会立刻有日志，说明写盘正常
- ❌ 别改成「启动时补写一条时间戳」之类 —— 那是**编造**没发生过的事

> **要判断「关机前那段聊了什么」，唯一可靠的依据是 `archive`**（原文层），
> 不是日志。日志记的是插件行为，archive 记的是对话内容。
> 但注意 `archive` 只从 v4（2026-11-14 04:45）开始，更早的没有回填。

### 4.3.1 ⚠️ `policyBytes` 预算只管**一个小节**，不是整个 `policy.md`

**2026-11-17 我在这里算错过一次，差点建议用户去删文件内容。**

当时看到 `policy.md` 有 **13851 字节**、而 `policyBytes` 预算 **8000**，
就断定「注入被截断了，后半段规则没生效」。**这个判断是错的。**

**实际代码行为**（`policyTextSync()`，`index.js` L3052）：

```
① 找「给模型的规则」标题行（正则 /^#{1,2}\s*.*给模型的规则/）
② 从该行下一行起，收到**下一个同级标题**为止  ← 只取这一段
③ activeLines() 过滤 → truncateBytes(text, policyBytes)
```

**所以**：只有「给模型的规则」那一节的字节数和 8000 比才有意义。
`policy.md` 其余部分（写记忆命令表、参数表、keywords 规则……）**根本不进注入**，
它们只是给人看的说明文档。

**实测（2026-11-17）**：

| 项 | 值 |
|---|---|
| `policy.md` 总字节 | 13851 |
| 「给模型的规则」小节 | L3 ~ L19，**1135 字节** |
| 预算 | 8000 |
| 实际占用 | **14%**，余量 6865 字节 |

**判据**：想知道有没有截断，**不要看 `Get-Item policy.md` 的 Length**。
要按「给模型的规则」索引节后单独量，或用 `_dbpreview/show-injection.mjs`
看「## 全局规则」那一段的实际字节数。

**推论**：挪动 `policy.md` 里的行号、把收尾语删了再加回去，**对注入零影响** ——
`policyTextSync` 按标题圈范围，`extractHeartbeat` 按行首前缀 `- 每轮…结尾` 找，
`restoreHeartbeat` 用正则原位替换，**三处都不依赖行号**。
唯一要求是收尾语那一行**保持那个格式**，且留在该小节内。

### 4.4 ⓘ 检索结果是「按表轮取」的，不是按相关度混排

> ⚠️ **用词**：注释、文档、注入里都别写「分层」—— 它会被读成「整块排完再下一块」，
> 而实际是**轮流**。2026-11-14 注入里写了「按表分层…不混排」，实测的人看到
> `profile → rules → logs → profile → …` 就判定「分层没生效」，白查一轮。
> 这个词的代价是真实的，见 `DECISIONS.md` D18.1。

**2026-11-14 改（D18.1）**：`search()` 不再把三张表的 bm25 混在一起排。

```
组内：score ASC（越小越相关，各表内部仍是真的相关度）
组间：profile → rules → logs 轮流各取一条
```

**为什么**：bm25 是**每张表各自语料**算的（文档数 / 平均长度 / 词频分布都不同），
跨表比大小没有意义。实测 `q=大肥鱼` 时 `logs -7.876` 会排在 `profile -4.668` 前面，
而后者才是「用户称呼 AI 为大肥鱼」的定义。

**因此**：

- 看到「结论型条目排在流水后面/前面」先确认 **table 字段**，别急着说排序坏了
- `limit` 很小（如 `summary=1` 取 3 条）时，三张表会各露一条 —— 这是**故意的**，
  不是「相关度算错」
- 改排序不要用「给 logs 加权」：那调的是 `logs_fts` 的列权重，跟跨表量纲无关

### 4.5 ⚠️「模型说写了、库里没有」—— 先看两条诊断

**2026-11-14 加（D18.2）**。写入本身几乎不失败（一天 108 次成功、0 次失败），
丢的是**解析**：实测 4.6% 的轮次「正文里有标记、一条都没落库」，其中两轮连日志都没有。

| 日志 | 含义 | 怎么修 |
|---|---|---|
| `[marker-unmatched]` | 有 `<!--mem-` 但正则零匹配（单行压缩 / 缺 `-->`） | 改写法，见 `AGENTS.md` 三条禁令 |
| `[marker-dropped]` + `reason:'empty-body'` | 正文被 topic 吃掉了（topic 与正文同行） | topic 只写分类名，正文换行写 |
| `[marker-dropped]` + 其它 reason | 库不可用 / 清洗后为空 / 写异常 | 看同轮其它日志 |

**正常写入只有 `[mem-写流水]`**，这两条只在失败时出现。

排查顺序：`[assistant-message] hasMarker:true` → 有没有 `[mem-写流水]`
→ 没有就看上面两条 → 都没有说明**这轮标记根本没被看见**（先怀疑热重载/重启）。

### 4.5.1 ★ 写流水 100% 触发的唯一已知方式（2026-11-18 定论）

> **一句话**：`log.ps1` 必须在**开始回答之前**执行 —— 不是「结尾」，不是「想起来」。
> 实测判据：这样做的轮次，`turn-stopping` 结算 `wroteThisTurn:true`。

#### 这个结论是怎么来的（别重复走弯路的那些假设）

2026-11-18 一整晚排查「约一半轮次漏记」，先后提出并**全部被数据否掉**的假设：

| 假设 | 否掉的实证 |
|---|---|
| 情绪导致忘了 | 情绪与 logs 是两条独立通道；有情绪轮照样写 |
| 纯闲聊轮不受触发 | #376「耳朵好软」是纯闲聊，记了且写明「没有任务」 |
| 有工具调用才写 | turn=35 调 4 次工具、13 步，`wrote=false`；turn=37 工具 0 次却写了 |
| 数据库连接静默失效 | `/state` 的 `db.ok=true`；隔离测试 18/18 全过 |
| 写入代码有 bug | 50 次连续写入全部成功（id 871–920，序号 1–50 无缺，10–102ms） |
| 判据错了 | `turn-stopping` **每轮必到**（299 次 / 296 轮）；同一注入相邻两轮结果相反 |

**真正成立的只有两条：**

1. **`wroteThisTurn:true` ⟺ 这一轮内确实执行了 `log.ps1`。** 没有例外、没有渐变，是二值事实。
2. **执行时机决定成败**：成功写入的 197 轮里，**193 轮（98%）发生在轮次中途**，
   只有 4 轮（2%）是「最后一刻才写」。所以「每轮结尾写」这条指令**实测几乎无效**。

#### 为什么必须是「回答之前」

实测时间线（`turn=70`，成功样本）：

```
22:21:19.897  user-message          ← 用户的话进来
22:21:25.809  archive-assistant step=1   ← 我开始思考
22:21:26.404  [mem-写流水] id=870        ← ★ 脚本送达（69ms）
22:21:31.245  archive-assistant step=2   ← 我才开始回答
22:21:37.129  write-streak-check wrote=true hits=1  ← 结算认账
```

**流水入库比回答落盘还早 ~5 秒。** 这条顺序有三个好处，都不是猜测：

- **内容更真**：回答之前写，记的是「刚读到什么、想到什么」；
  回答完之后补，记的是「我上一条说了什么」——后者容易变成复述。
- **有落点**：回答完之后注意力已经转向下一件事，「结尾」这个时机没有触发物。
- **可验证**：`turn-stopping` 的 `wroteThisTurn` 能给出确定的是/否。

#### 两条互相冲突的文案（**改注入时注意**）

同一套注入里，两条指令的时机是矛盾的：

| 位置 | 原文 | 实测效果 |
|---|---|---|
| `policy.md`「给模型的规则」段 | 「每轮**结尾**，先写流水，再加收尾语」 | ❌ 198 次成功里只占 2% |
| `usageLines`（`index.js` L4045） | 「**回复用户之前**调用一次」 | ✅ 98% 的成功形态 |

**保留后者。** 若将来统一文案，以「回答之前」为准。

#### 诚实边界：这不等于「永不漏」

执行者仍然是模型，**触发率不是 100%，只是提高**。程序只能保证：

- 检测 100%（`turn-stopping` 每轮必到，一定能知道这轮写没写）
- 写入链路 100%（50 次压测零失败）

⚠️ 因此**不要**把这条当成「已经解决漏记」。它是**目前唯一已知的高成功率形态**，
新会话应照它执行，但**不要宣称漏记已被消灭**。

#### 已知的静默失败面（都实测过）

| 面 | 现象 | 判据 |
|---|---|---|
| `WRITE_FAIL_NUDGE_ENABLED=false` | 漏记**不会提醒**，必须人工看流水 | `index.js` L5758 |
| `sessionId` 两边不对称 | `/log` 侧 `.trim()`，`turn-stopping` 侧不 trim → 键不同则「写了判没写」 | 正常时两边值相等（实测 44 字符一致） |
| 诊断日志时区 | 2026-11-18 前写 UTC、文件名用本地日期，**本地 00:00–08:00 日期对不上** | 已修，见 `diagTimestamp()` |

### 4.6 ⚠️ 改完 Host 代码别信 HMR：一律「禁用→启用」插件

**2026-11-14 两次实测，坏法还不一样。**

一、**只重装入口**。改完 `db-store.mjs` 的 `search()`，日志里有 `[apply-start]`、
注入文案（来自 `index.js`）已经是新的，但 `search` 行为**还是旧的**。
原因：HMR 重装插件入口 `index.js`；它静态 `import` 的 `db-store.mjs` / `db-schema.mjs`
在 Node 模块缓存里，**进程内不会重新求值**。于是「新入口 + 旧存储」并存，**零报错**。

二、**干脆不触发**。改 `index.js` 里的注入文案，日志里**连 `[apply-start]` 都没有**，
下一轮注入还是旧句子。DSH 重启后的新进程里尤其容易这样。

**结论**：别指望 HMR，也别把「日志里有 `[apply-start]`」当生效判据。
改完 **禁用 → 启用**（`include:dsh-memory`），不用重启 DSH。
`db-schema.mjs` 上最危险 —— 结构变更没生效时，代码以为迁移过了、库还是旧结构。

**唯一的生效判据是行为**：注入文案看下一轮注入，`search` 看排序，schema 看 `/state` 的字段。

### 4.11 ★ 新增「后台链路」时，要补的五处（2026-11-21 补记模块的教训）

1.4.0 加了补记（漏记自动补写）—— 那是一整条**后台链路**，
它在 `turn/end` 之后异步跑、平时看不见。这类改动**比普通 bug 修复漏得更多**，
因为界面上没有任何变化可供对照。

**五处必补**（缺任何一处，下一个人就会找不到它）：

| # | 补哪 | 为什么 |
|---|---|---|
| ① | `docs/项目地图.md` 新开一节 | 地图是「动手前先读」的结构索引。补记整块当初**在地图里零位置**，等于不存在 |
| ② | `CHANGELOG.md` 记一条 | 后台行为用户看不见，只能靠 CHANGELOG 知道「有过这回事」 |
| ③ | 回归脚本 + 进 `SCRIPTS` | 见下方「为什么补记那批一个脚本都没有」 |
| ④ | `AGENTS.md` 记**判据级**的坑 | 只写「改了什么」没用，要写「以后遇到什么情况该停下来想」 |
| ⑤ | 包内 `README.md` 告诉用户「怎么知道它在工作」 | 后台链路的最大风险是**用户以为它没跑**，或**以为跑了其实没跑** |

**为什么补记那批一个脚本都没有**（2026-11-21 实测）：

```
grep 'backfill' _dbpreview/     → 0 处
```

原因是两个「看起来查过了」的假象叠加：

- `verify-functions` 报「无新增死代码」—— 但它的覆盖边界明写着
  **「只检查 `function` 声明，`const x = () => {}` 不在范围内」**，
  而补记那套**全是箭头函数**；
- 回归 `TOTAL=73 FAIL=0` 全绿 —— 它只证明**别的部分**没被改坏。

**判据**：加了一个新功能后，先跑

```powershell
Get-ChildItem _dbpreview\*.mjs | Select-String -Pattern '<模块关键词>' -SimpleMatch
```

**命中 0 处 = 零覆盖**，没有「可能在别处测过」这种可能。

**并且：给后台链路写测试时，必须有「反向守卫」。**
补记的记账拦截如果写成恒真（`!== undefined` / 漏个 `!`），
会让**所有**正常写入都不再记账 → 每轮判「没写」→ 补记对每轮都触发。
只测「该拦的拦了」会让这种情况下**全绿通过，而系统已废**。

## 5. 文档与记忆的边界

| | 文档（`docs/`、`AGENTS.md`、`README`） | 记忆（memory.db） |
|---|---|---|
| 位置 | 项目目录，进 git | 记忆根目录，运行时数据 |
| 读者 | 下一个会话的我（启动时读一次） | 下一个会话的我（每轮注入） |
| 预算 | 65536 字节，可以啰嗦 | 项目段 4096 字节，必须精炼 |
| 内容 | 怎么开发维护、完整流程、踩坑细节 | 每轮都必须知道的约定与事实 |

**判断标准不是「给谁看」，而是「多久看一次」+「失效了会怎样」：**

- **每一轮都要用，且删了也不会失传** → 记忆（`rules` / `profile`，用户在 GUI 维护）
- **偶尔要查、但要完整** → 这份文件
- **只是这次的过程记录** → 流水（`logs` 表）

> ⚠️ **不要把长期有效的约定只放在 `rules` 里。**
> `rules` 是运行时数据，用户在 GUI 里随时会增删（实测从 84 条删到 7 条）。
> 一旦删掉，新会话的模型就再也看不到那条要求了 —— **没有副本就没有恢复的可能**。
> 反过来，写进 `AGENTS.md` 的内容跟着仓库走，不会因运维操作丢失。
>
> 所以：**跨会话必须一直生效的行为要求，至少要在 `AGENTS.md` 留一份。**

## 5.1 2026-11-17 两批修复里最值得记的四个坑

这一轮修了 12 个 bug（第一批 7 个 + 第二批 5 个），全部有回归用例 + 故障注入。
**下面只写「以后还会再犯」的那几个**，完整清单见 `CHANGELOG.md` 1.3.0。

### 5.1.1 `String.replace` 的 `$` 展开会改写整份用户文件

**问题**：收尾语（`policy.md` 里那一行）如果含 `$&` / `$'` / `` $` `` / `$1`，
用 `str.replace(needle, 用户文本)` 替换时，**这些是替换模式而不是字面量**。

**实际后果**：`$&` 会被展开成「匹配到的那段」，于是一行收尾语能**复制粘贴
出整份 `policy.md` 的内容** —— 用户的数据文件被静默改写，且没有任何报错。

**修法**：替换值必须走函数形式 `str.replace(needle, () => 文本)`，
或者先转义 `$`（`文本.replace(/\$/g, '$$$$')`）。**函数形式更稳妥**，
因为它不做任何模式解析。

**判据**：只要你的 `replace` 第二个参数**来自用户数据**，就不是字面量替换。

### 5.1.2 `joinWithBudget` 要防「全军覆没」

**问题**：按预算逐条塞进注入时，它是「塞不下就跳过这一条」。
于是**单条就超预算**的规则会被永远跳过 —— 实测那条 1400 字的红线规则
在注入里**一个字都没有**，而注入看起来是正常的（只是少了一条）。

**修法**：兜底判据是「一条都没塞进去」→ 取最长的那条硬截断塞进去。
**「宁可截断也不能整条消失」**：截断的规则还能看到一半，消失的规则等于不存在。

**同源**：这与 `AGENTS.md` 里「静默失效比报错更难查」是同一类问题 ——
它的症状不是报错，而是「注入里少了一条你以为在的规则」。

### 5.1.3 `isInside` 这类包含判断，参数顺序写反了照样「看起来能用」

**问题**：`isInside(a, b)` 本意是「b 在 a 里面吗」。参数传反后，
**绝大多数情况下返回值恰好也对**（路径相近），只有「迁到子目录」这一种输入才暴露。

**实际后果**：把记忆迁到一个子目录时守卫放行 → **复制自己进自己的子目录**，
递归嵌套，体积翻倍。

**修法**：改成 `isInside(容器, 内容)` 并在函数名/注释里写死这个方向。

**教训**：**对称函数（`a` 与 `b` 可交换）写错顺序，测试很容易全绿。**
写 `assert(isInside(parent, child))` 之外，**必须再写一条反例**
`assert(!isInside(child, parent))` —— 只测正例的话，参数反了也是绿的。

### 5.1.4 入参校验要「先判类型形态，再判范围」

**问题**：`Number(body.id)` 太宽容 ——

| 传入 | `Number()` 得到 | 后果 |
|---|---|---|
| `true` | `1` | **软删掉 id=1 的真实记忆** |
| `[7]` | `7` | 改掉 #7 |
| `null` | `0` | 命中 id=0（通常无意义，但仍是错的目标） |
| `"7abc"` | `NaN` | 后续静默不匹配 |

`limit` 那边则相反：`-1` 静默返回 0 条（**看着像「没有这段记忆」**）、
`2.5` / `1e21` 直接 500、`0` 被 `||` 兜成默认值（用户传 0 想「不返回」，
实际拿到 30 条）。

**修法**：`parseId()` 只认 number 或纯数字字符串，其余返回 `null`；
`clampInt()` 先判**整数形态**再判范围。两处都**把 5~6 个调用点收口成 1 个函数**。

**为什么必须收口**：这类校验分散在各路由里时，**新加一条路由就会漏一次**。
2026-11-17 实测：同一条 `Number(body.id)` 在 6 处出现，改之前没人发现它们其实是同一个问题。

**判据**：同一个「入参清洗」逻辑出现第 2 次，就该抽函数，不要等到第 6 次。

### 5.2.1 「恒真/恒假分支」——不只是测试
- **写生产代码也要防「恒真/恒假分支」—— 不只是测试**（2026-11-16 第三次同病）：
  上面那条管的是**测试**里的恒真断言。但**生产代码里同样会出现**，
  而且更隐蔽：它不影响正确性，所以测试全绿、`node --check` 通过、
  行为验证也通过 —— 于是没人发现。

  实际踩过（2026-11-16，修 `atomicWrite` 时我自己写出来的）：

  ```js
  const backupPath = `${targetPath}.${process.pid}.bak`
  let moved = false
  try {
      await rename(targetPath, backupPath)
      moved = true                      // ← 赋值
  } catch (error) {
      await unlink(tempPath).catch(() => {})
      throw error                       // ← 失败直接抛，根本走不到下面
  }
  ...
  if (moved) await unlink(backupPath)   // ← 恒为 true，这个判断没有意义
  ```

  **判据**：一个布尔变量若在「能继续往下走的所有路径上」都等于同一个值，
  那读它的分支就是死代码。

  **为什么必须写这条**：这是同一天里第三次同源问题 ——
  `reportBudget` 静默失效（函数在、调用点没了）、恒真断言 `check(name, true)`、
  这次的 `if (moved)`。三次都不是语法错误，`node --check` 全部通过。

  **规矩**：
  - 写 `if (flag)` 之前问一句：**有没有哪条路径能让它走到这里时是另一个值？**
    答不出来就说明这个 flag 该删，或者该改成真正会变化的量；
  - 反向也一样：**不在所有路径上赋值的变量，可能是 undefined**（恒假）；
  - 复查自己刚写的代码时，这类问题**排在最前面**——因为它没有症状。
  - 与测试那一条的关系：这是**同一个病在生产代码里的形态**，
    所以判据也一样 —— **分支必须能被某条真实路径走到两个方向**。

### 5.2.2 「距今 N 分钟」——会随时间自然变红的断言
- **不要写「距今 N 分钟」这类会随空闲时长自然变红的断言**（2026-11-16 第三次同病，换了个形态）：
  `selfcheck-log-alive` 原来是「最近一条流水距今 ≤30 分钟」。
  用户歇了 7 小时 45 分回来，它立刻报 466 分钟前 —— **而通道完全正常**。
  **一个会随时间自然变红的断言，等于没有断言**：人会开始忽略它，然后是整个套件。

  **判据**：断言里出现 `Date.now() - <数据时间戳>` 的比较，先问
  「这个差值变大是因为**被测量的东西坏了**，还是仅仅因为**没人用**？」
  答不出前者就说明它测的不是状态，是使用频率。

  **修法（最终形态，前两版都已废弃）**：**把这件事移出回归**。
  「模型写没写流水」由运行时 `writeFailStreak` 按轮计数兜住 ——
  那是**正确的时机**（轮次结束的当下），而回归只在我跑测试时才看一眼，既晚又不可靠。
  回归里只留「进程活着」这一个维度，见下一条。

  > ⚠️ **但这条防线没接上**：`WRITE_FAIL_NUDGE_ENABLED = false`（2026-11-18 用户关的，
  > steer 会让本轮多跑一步、表现为「打嗝」约 8 秒）→ **提醒分支被短路，一次都不触发**。
  >
  > **📌 2026-11-21：漏记已有兜底 —— 是「补记」不是「提醒」。**
  > 提醒仍关；补记（`turn/end` → `prepareCall` → POST）生效，但**只做事不报告**
  > （只写 `backfill-done`，界面无感）。它出现得多 = 模型自己漏得多。

  **阈值 2026-11-17 从 4 降到 2、傍晚再降到 1**（用户定，现为
  `WRITE_FAIL_STREAK_LIMIT = 1`）。
  4→2 的理由：当晚两次漏记的规模都是 **3 轮**
  （01:48–01:53 连续三轮只给分析结论没动文件；04:30 前后连续四轮纯回答型），
  阈值 4 意味着「3 轮漏记永远不报警」—— **防线在最常见的漏记规模上失效**。
  2→1 的理由：阈值 2 等于「第 1 轮必然漏」，而实测漏记率约 50%，
  **每两轮就有一条流水永远没人补**。日志证据：旧代码 `08:44:20 streak=1` 不提醒、
  `08:44:50 streak=2` 才提醒；新代码 `08:53:55 {"streak":1,"limit":1,"delivered":true}`
  立刻提醒。
  ⚠️ 但**不要指望它兜住一切**：它只在「本轮确实没写」时计数，间隔太短也来不及响。
  **它没有误报**（2026-11-17 实测确认，见下条）。

  **阈值 1 的必要配套是防无限循环闸门**（`fatfishSteerGuard` /
  `FATFISH_STEER_GUARD_KEY` / `alreadyNudgedThisTurn`）：
  DSH 的 `agent/turn-stopping` 契约写明在它里面 `steer` 会让**本轮不关闭、多跑一步**，
  所以阈值 1 后每个漏记轮都会 steer，**没有闸门就是无限循环**，会烧光 token 并可能卡死客户端。
  设计是**每个 turn 最多 steer 一次**，第二次直接放行 —— **宁可漏一次，也不能循环**。
  闸门键前缀取 `` `${PLUGIN_SOURCE_KIND}:steer` ``（带包名，防与其他插件撞名）。
  ⚠️ **改阈值前先看闸门在不在**；只把 2 改成 1 而不带闸门是危险改动。
